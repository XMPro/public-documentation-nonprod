Deploy XMPro on AWS Kubernetes (EKS)

Introduction

Get XMPro running on Amazon Elastic Kubernetes Service (EKS) with Terraform automation. This is the Kubernetes-native AWS deployment for the 5.0 platform.

Deployment uses a three-layer model designed for shared clusters: one EKS cluster (with its platform controllers) can host multiple isolated XMPro sites, each with its own databases, KMS key, DNS subzone, and Helm release. Additional Stream Hosts are deployed through a small fourth layer.

Layer Applied Contains
1 - Cluster (infra-k8s) Once per cluster VPC, EKS cluster, AWS Load Balancer Controller, Envoy Gateway, cert-manager, External Secrets Operator, GatewayClass, pre-allocated gateway NLB EIPs
2 - Site infrastructure (infra) Once per site RDS SQL Server + databases, KMS key, Route53 subzone + wildcard A record
3 - Site application (app) Once per site Per-site secret store (AWS Secrets Manager → Kubernetes), per-site Gateway + Let's Encrypt Issuer, XMPro Helm release, HTTPRoutes
4 - Stream Hosts (stream-hosts) Per site, as needed One standalone Stream Host per Collection
5 (optional) - AI backing services (infra-ai) Coming soon Milvus, Neo4j, TimescaleDB and Mosquitto for the AI product's RAG features
Note

This guide works on Windows, Mac, and Linux. Windows users should use Command Prompt or PowerShell. The deployment requires terraform, aws, and kubectl on PATH.

Provision Infrastructure Your Own Way?

Note

Infrastructure provisioning is your responsibility. The infrastructure layers (infra-k8s, infra) are templates: they show how XMPro provisions these resources internally, and you can use them as-is, adapt them, or replace them entirely with your own provisioning. Only the application layer (app) is the deployment interface the platform requires; it consumes whatever infrastructure you point it at. The Terraform module in this guide is provided as an example only and is not officially supported by XMPro: you are responsible for infrastructure configuration, maintenance, and support. See the Deployment Responsibility Matrix for details.

Tip

The example module uses t3.medium (system) and t3.large (app) node instance types and a db.t3.small SQL Server Express RDS by default, suitable for development and evaluation. SQL Server Express has a 10 GB per-database cap; use sqlserver-se or higher for production. See the module README for production sizing.

You can provision the required infrastructure using:

  • The example Terraform module (community-supported)
  • The AWS console (ClickOps)
  • Your organization's infrastructure-as-code tools

Summary of resources created by the infra-* layers:

The table below lists the resources the template layers (infra-k8s, infra) provision. Provision them yourself any way you like, the application layer (app) only consumes them.

Note

Autoscale is not currently supported on Kubernetes (it is in development). XMPro's shared-session handling does not yet work correctly behind a load balancer with multiple replicas, so each product runs a single replica and ElastiCache Redis is not used. The create_redis_cache toggle and enable_autoscale flag exist only to back this future capability, leave them off.

Once you've created these resources, you still need Steps 1-4 (install the CLI tools, sign in to AWS, confirm your registry credential, and clone the module for its app layer), then skip ahead to Step 8: Deploy the Site Application Layer and provide the details in your configuration.

Traffic flow: https://{ad,ds,sm,ai}.<site-zone> → NLB (static EIPs) → Envoy Gateway → HTTPRoute → product Service. The sm. hostname is path-split: /identity/* routes to the Identity Server (IS); everything else routes to Subscription Manager (SM).

Cluster-Level Components

Layer 1 installs a fixed set of platform components into the cluster, once per cluster. Every site's application layer assumes they are already present: layer 3 creates only per-site resources - the secret store, Gateway, Issuer, HTTPRoutes and Helm release - and binds them to these shared components. Adding a site never installs or upgrades any of them.

Component Namespace Purpose
AWS Load Balancer Controller kube-system Provisions and manages the NLB fronting the gateway
Envoy Gateway envoy-gateway-system Gateway API data plane; provides the GatewayClass the sites' Gateway resources bind to
cert-manager cert-manager Issues Let's Encrypt certificates for product hostnames via HTTP-01
External Secrets Operator external-secrets Syncs AWS Secrets Manager bundles into Kubernetes Secrets the chart consumes
istio-base istio-system Istio CRDs
istiod istio-system Istio control plane and sidecar injection
istio-cni kube-system Istio CNI plugin; enables unprivileged sidecars so Pod Security baseline can be enforced

If you build the cluster yourself instead of applying layer 1, these are the components you install. Provision Infrastructure Your Own Way? lists them alongside the rest of the infrastructure the application layer expects.

To confirm what an existing cluster already has:

All platforms:

helm list -A
Note

Istio CNI and Pod Security. Because layer 1 installs Istio CNI, injected pods use the unprivileged istio-validation init container rather than the classic sidecar init container (which needs NET_ADMIN and root). Pod Security baseline admits that container, so the application layer's pod_security_enforce defaults to baseline and enforcement is active on each site namespace. The Azure Kubernetes deployment does not install Istio CNI and defaults pod_security_enforce to "", leaving enforcement disabled.

Prerequisites

You need:

  • An AWS account with permissions for VPC, EKS, EC2, RDS, ElastiCache, IAM, KMS, Secrets Manager, Route53, and CloudWatch
  • Room in the VPCs per Region service quota in your target region. The cluster layer creates one VPC, and the default quota is 5 per region
  • A computer with internet access
  • A GHE account with read access to {{TERRAFORM_EKS_MODULE_URL}}, for cloning the deployment files
  • A GHE personal access token with read:packages, for pulling the container images from {{ACR_URL}}
Important

How to get access. Request it through your XMPro point of contact, consultant, or personnel. They raise it internally; XMPro provisions your named users and grants your organisation read access to the deployment repository and container images. Access is per-person and tied to the account XMPro issues you — there is no public download and no self-signup.

Check the VPC quota before you start. The VPC is the very first resource the cluster layer creates, so an account already at the quota fails seconds into the apply with VpcLimitExceeded. Compare the quota against the VPCs you already have:

All platforms:

aws service-quotas get-service-quota --service-code vpc --quota-code L-F678F1CE --region us-west-2 --query "Quota.Value" --output text
aws ec2 describe-vpcs --region us-west-2 --query "length(Vpcs)"

If the count has reached the quota, delete a VPC you no longer need, deploy into a different region, or request an increase:

aws service-quotas request-service-quota-increase --service-code vpc --quota-code L-F678F1CE --desired-value 10 --region us-west-2 --query "RequestedQuota.Id" --output text
Important

A requested increase is not an approved increase. From the moment the request is filed, aws service-quotas get-service-quota reports the requested value (for example 10.0) even while the request is still pending, and EC2 keeps enforcing the old limit. The quota check above therefore looks like it passed and the apply still fails. The authoritative check is the status of the request itself, using the request id returned by the command above:

aws service-quotas get-requested-service-quota-change --request-id <request-id> --query "RequestedQuota.Status" --output text

Wait until this reads APPROVED before applying the cluster layer. PENDING or CASE_OPENED means the old limit is still in force.

2. Login to AWS

All platforms:

aws configure              # Long-lived access keys
# OR
aws sso login              # AWS IAM Identity Center / SSO

# Verify
aws sts get-caller-identity
Tip

Terraform automatically uses your AWS CLI credentials. For CI/CD pipelines, prefer OIDC federation over long-lived keys.

3. Registry Authentication

XMPro's container images live in {{ACR_URL}} and are not anonymously pullable. Confirm your credential works now — this fails in seconds, where a bad or expired token otherwise surfaces as ImagePullBackOff fifteen minutes into an apply.

All platforms:

read -rs GHE_PAT            # prompts, so the token never lands in shell history
printf '%s' "$GHE_PAT" | docker login containers.xmpro.ghe.com -u YOUR-GHE-USERNAME --password-stdin
docker manifest inspect {{ACR_URL}}/ad:{{VERSION}}

Both commands must succeed before you continue.

Important

That login authenticates you, not the cluster. Terraform does not pull images — the cluster nodes do, using a pull secret inside the namespace. You supply the credentials once, in the application layer (step 8), and it creates that secret for you. Logging in locally and skipping the Terraform variables leaves every pod in ImagePullBackOff.

Pull secrets are namespaced, so one is created per site rather than per cluster. Pulls from containers.xmpro.ghe.com must be authenticated: either set registry_username and registry_password in the application layer, or create the secret yourself and name it in image_pull_secrets. Leaving both empty fails at plan rather than surfacing as ImagePullBackOff. If you mirror the images into your own ECR, leave both empty — the node IAM role handles the pull and no secret is created.

Mac/Linux:

git clone {{TERRAFORM_EKS_MODULE_URL}}.git terraform-k8s

At minimum, edit these values in terraform.tfvars:

company_name = "yourco"          # Drives resource and database naming

Important

Warning

Do not use xmpro as company_name. It collides with a hardcoded XMPro company in the SM database migration scripts (case-insensitive unique constraint).

5. Deploy Layer 1 - Cluster

The cluster layer configures Kubernetes/Helm providers from the EKS cluster it creates, so a first (greenfield) apply must be done in two phases: create the VPC and cluster first, then apply the rest (the platform controllers, which need a reachable cluster):

All platforms:

terraform init

# Phase 1 - VPC + EKS cluster (so the k8s/helm providers can connect)
terraform apply -target=module.cluster.module.vpc -target=module.cluster.module.eks_cluster

# Phase 2 - platform controllers, GatewayClass, gateway EIPs
terraform apply
Important

Phase 1 must target module.cluster.module.vpc as well as the cluster. Targeting only the cluster prunes the NAT gateways/public subnets from the plan: nodes then come up with no egress to ECR, can't pull the CNI image, and fail to join (NodeGroup CREATE_FAILED: "Instances failed to join the kubernetes cluster").

This creates the VPC, EKS cluster, AWS Load Balancer Controller, Envoy Gateway, cert-manager, External Secrets Operator, Istio (base + istiod + Istio CNI, with the shared gateway joined to the mesh), the GatewayClass, and the pre-allocated gateway EIPs. Takes about 15-20 minutes. You do this once per cluster, additional sites reuse it. See Cluster-Level Components for what each of these controllers does and the namespace it lands in.

Point kubectl at the new cluster. Run terraform output and copy the values into the command (later steps reuse them):

All platforms:

terraform output
# Note: cluster_name, eks_cluster_oidc_provider_arn, eks_cluster_oidc_provider_url,
#       vpc_id, private_subnet_ids, public_subnet_ids, node_security_group_id,
#       gateway_class_name, gateway_eip_public_ips, irsa_xmpro_role_arn

Then update kubeconfig using the cluster_name value:

All platforms:

aws eks update-kubeconfig --name eks-yourco-dev --region us-west-2

Mac/Linux (substitute straight from Terraform instead of copy/paste):

aws eks update-kubeconfig --name "$(terraform output -raw cluster_name)" --region us-west-2

6. Deploy Layer 2 - Site Infrastructure

Windows (PowerShell):

cd ..\infra
Copy-Item terraform.tfvars.example terraform.tfvars

Windows (Command Prompt):

cd ..\infra
copy terraform.tfvars.example terraform.tfvars

Mac/Linux:

cd ../infra
cp terraform.tfvars.example terraform.tfvars

Edit terraform.tfvars, reusing the cluster VPC and pointing the wildcard DNS at the gateway EIPs (both from layer 1 outputs):

company_name = "yourco"
name_suffix  = "site1"           # Unique per site on this cluster
aws_region   = "us-west-2"

# Reuse the cluster VPC (from layer 1 outputs) - no new VPC
create_vpc             = false
vpc_id                 = "vpc-xxxxx"
private_subnet_ids     = ["subnet-aaa", "subnet-bbb", "subnet-ccc"]
public_subnet_ids      = ["subnet-ddd", "subnet-eee", "subnet-fff"]
node_security_group_id = "sg-xxxxx"

# --- Database ---
db_admin_username  = "xmadmin"
db_admin_password  = "ChangeMe123!Strong"   # see RDS password rules below
db_engine          = "sqlserver-ex"          # sqlserver-se/-ee for production
db_engine_version  = "15.00"
db_instance_class  = "db.t3.small"

# --- Redis ---
# Redis is only consumed by autoscale, which is NOT currently supported on
# Kubernetes (in development). Leave false - no ElastiCache is provisioned.
create_redis_cache = false

# --- DNS ---
enable_custom_domain = true
dns_zone_name        = "site1.xmpro.yourco.com"
# Wildcard A record (*.site1...) → gateway NLB EIPs (layer 1 gateway_eip_public_ips)
cluster_gateway_eip_public_ips = ["52.x.x.x", "13.x.x.x"]
Important

RDS password rules. RDS rejects the master password if it contains /, @, ", or a space: the apply fails with InvalidParameterValue: MasterUserPassword is not a valid password. Use 8+ printable ASCII characters mixing upper/lower/digit and a symbol from the allowed set (e.g. ! # $ % ^ & * - _). Set the same value in the application layer's db_admin_password (Step 8).

Apply:

terraform init
terraform plan    # Validates config; most input mistakes fail here, not mid-apply
terraform apply
Tip

Always run terraform plan first. It validates the configuration and reads existing state from AWS without creating anything, so most input mistakes - a typo in a subnet id, a missing required variable - cost you seconds instead of a failed apply you have to unpick. It does not perform AWS service-side validation: an RDS password containing a disallowed character still plans cleanly and fails during terraform apply. With the default options a healthy plan for this layer ends with a line like Plan: 9 to add, 0 to change, 0 to destroy. - the resource count changes with the module settings you enable.

This creates the site's RDS SQL Server (with the SM, AD, and DS databases), KMS key, and Route53 subzone with the wildcard A record. Takes about 10-15 minutes, RDS is the long pole.

Verify before continuing

Collect the values Step 8 needs. Two of them are marked sensitive, so plain terraform output prints <sensitive> instead of the value - use -raw for those:

All platforms:

terraform output

terraform output -raw rds_endpoint
terraform output -raw route53_zone_id
terraform output -raw secrets_kms_key_arn

Sample output (values are examples, use your own):

ad_database_name = "XMPro_AD_yourco"
db_admin_password = <sensitive>
dns_zone_name = "site1.xmpro.yourco.com"
ds_database_name = "XMPro_DS_yourco"
rds_endpoint = "rds-yourco-site1.cf0px0jf6636.us-west-2.rds.amazonaws.com"
rds_port = 1433
route53_zone_id = "Z0567878QMDCMEUPLHCC"
secrets_kms_key_arn = <sensitive>
sm_database_name = "XMPro_SM_yourco"
Tip

Keep this output open. Every value in it is copied into the application layer's terraform.tfvars in Step 8.

7. Point DNS at the Gateway

Before deploying the application layer, the site's hostnames must resolve publicly. cert-manager's Let's Encrypt HTTP-01 challenge fails otherwise, and without a certificate the SM and IS products never start.

Pick one of the two options below.

Option A - Point A records at the gateway (simplest)

Use this when your DNS is hosted anywhere other than Route53 (GoDaddy, Cloudflare, your corporate DNS), or when you simply want the fewest moving parts.

Set enable_custom_domain = false in the layer 2 terraform.tfvars so no Route53 subzone or wildcard record is created, then create four A records in whatever DNS provider you already use, all pointing at the gateway EIPs from layer 1 (terraform output gateway_eip_public_ips):

ad.site1.xmpro.yourco.com   A   52.x.x.x
ds.site1.xmpro.yourco.com   A   52.x.x.x
sm.site1.xmpro.yourco.com   A   52.x.x.x
ai.site1.xmpro.yourco.com   A   52.x.x.x   (only if enable_ai = true)

route53_zone_id is only meaningful when the zone lives in Route53. If your DNS is hosted elsewhere, leave it empty (or omit it) in Step 8; if the zone is in Route53 and you created the A records there, pass that zone id. Then skip to Verify before continuing.

Option B - Delegate a Route53 subzone (if you own the parent zone in Route53)

Layer 2 created a subzone for the site. Its parent zone must delegate to it. Get the subzone's nameservers:

terraform output route53_name_servers

Add an NS record in the parent zone for the subzone pointing at the four nameservers shown:

aws route53 change-resource-record-sets --hosted-zone-id <PARENT_ZONE_ID> --change-batch '{
  "Changes": [{
    "Action": "UPSERT",
    "ResourceRecordSet": {
      "Name": "site1.xmpro.yourco.com", "Type": "NS", "TTL": 300,
      "ResourceRecords": [{"Value": "ns-1.awsdns-00.org"}, {"Value": "ns-2.awsdns-00.com"}, {"Value": "ns-3.awsdns-00.co.uk"}, {"Value": "ns-4.awsdns-00.net"}]
    }
  }]
}'
Important

Wait for the delegation to propagate before applying the app layer. A freshly-delegated zone can take a few minutes to resolve from all of Let's Encrypt's validation vantage points: applying too early can make the first certificate order fail a challenge, after which cert-manager backs off (up to ~1 hour) before retrying. Recovery is to kubectl delete certificate xmpro-le-tls -n <name_suffix> and re-apply.

Verify before continuing

Whichever option you used, confirm every enabled hostname resolves to the gateway EIPs before applying the application layer. Option A creates one A record per product, so checking only ad will miss a record you forgot and the omission surfaces later as a failed certificate order. Check ad, ds and sm, plus ai when enable_ai = true:

Windows (PowerShell):

"ad","ds","sm","ai" | ForEach-Object { Resolve-DnsName "$_.site1.xmpro.yourco.com" -Type A }

Mac/Linux:

for h in ad ds sm ai; do echo -n "$h: "; dig +short $h.site1.xmpro.yourco.com; done

Sample output (your EIPs will differ):

ad: 52.34.116.201
ds: 52.34.116.201
sm: 52.34.116.201
ai: 52.34.116.201

Drop ai from the list when enable_ai = false. If any hostname returns nothing, or returns anything other than your gateway EIPs, stop here. Applying the application layer now will fail certificate issuance and put cert-manager into a back-off that takes up to an hour to clear.

8. Deploy the Site Application Layer

Windows (PowerShell):

cd ..\app
Copy-Item terraform.tfvars.example terraform.tfvars

Windows (Command Prompt):

cd ..\app
copy terraform.tfvars.example terraform.tfvars

Mac/Linux:

cd ../app
cp terraform.tfvars.example terraform.tfvars

Edit terraform.tfvars with values from layers 1 and 2:

aws_region   = "us-west-2"
company_name = "yourco"
name_suffix  = "site1"

# [from layer 1]
cluster_name          = "eks-yourco-dev"
irsa_xmpro_role_arn       = "arn:aws:iam::<account>:role/irsa-xmpro-yourco-site1"
cluster_oidc_provider_arn = "arn:aws:iam::<account>:oidc-provider/oidc.eks.us-west-2.amazonaws.com/id/<id>"
cluster_oidc_provider_url = "https://oidc.eks.us-west-2.amazonaws.com/id/<id>"
gateway_class_name        = "eg"     # [from layer 1] gateway_class_name

# [from layer 2]
rds_endpoint        = "rds-yourco-site1.<id>.us-west-2.rds.amazonaws.com"
rds_port            = 1433
ad_database_name    = "XMPro_AD_yourco"
ds_database_name    = "XMPro_DS_yourco"
sm_database_name    = "XMPro_SM_yourco"
ai_database_name    = ""             # from layer 2 output if enable_ai = true
secrets_kms_key_arn = "arn:aws:kms:us-west-2:<account>:key/<id>"
route53_zone_id     = "Z0000000000000000"

# --- RDS master credentials (must match the layer-2 tfvars) ---
db_admin_username = "xmadmin"
db_admin_password = "ChangeMe123!Strong"

# --- Container images ---
image_registry     = "{{ACR_URL}}"
image_tag          = "{{VERSION}}"

# Creates the pull secret in this site's namespace. Both values are written to
# Terraform state. Leave empty when mirroring into ECR and pulling via IRSA.
registry_username  = "YOUR-GHE-USERNAME"
registry_password  = "YOUR-GHE-PAT"

# Names of pull secrets provisioned out of band, merged with the one above.
image_pull_secrets = []

# --- Company admin (passwords are generated into the secret bundle) ---
# email is a contact address only; the login username is derived separately (see below)
company_admin_first_name    = "Admin"
company_admin_last_name     = "User"
company_admin_email_address = "admin.user@yourco.com"

# --- Licensing ---
# is_evaluation_mode = true uses the built-in evaluation product IDs and keys.
# Setting it false REQUIRES you to supply every product ID and key yourself.
is_evaluation_mode = true
enable_licenses    = true

# --- Ingress / DNS / TLS ---
enable_custom_domain = true
dns_zone_name        = "site1.xmpro.yourco.com"
letsencrypt_email    = "ops@yourco.com"   # receives Let's Encrypt expiry notices

# --- Features ---
enable_ai        = false
enable_autoscale = false           # leave false - autoscale is not currently supported on Kubernetes (in development)
Warning

is_evaluation_mode is required. It defaults to false, and when false the apply fails during terraform plan unless every product ID and key is set. For an evaluation or QA install, set is_evaluation_mode = true as shown. This is the single most common reason a first deploy stops before creating anything.

Note

Istio and Pod Security default to on. examples/layered/app deploys with Istio injection enabled and the baseline Pod Security Standard unless you say otherwise. The enable_istio, istio_peer_authentication, pod_security_standard and pod_security_enforce variables are all settable here. Istio injection requires istiod on the cluster, which the cluster layer installs in Step 5; if you disabled it there, set enable_istio = false.

Note

External Secrets Operator needs no per-site configuration. It is a cluster-wide component, installed once by the cluster layer in Step 5. Every site's application layer wires itself to that shared install automatically - creating only its own secret store and the access grant for its own KMS key - so there is nothing to set here, and nothing to change when you add further sites to the cluster.

Note

The application reads every credential from one aggregate AWS Secrets Manager bundle (xmpro/<name_suffix>/secrets), which External Secrets Operator materializes into the cluster as the xmpro-secrets Kubernetes Secret. There are no separate per-credential bundles.

Note

Where the pull secret comes from. registry_username and registry_password make this layer create the dockerconfigjson secret in the site namespace and wire every workload to it. image_pull_secrets is for secrets you provisioned yourself - the two are merged. External Secrets Operator cannot serve this: its bundles are type Opaque, and Kubernetes ignores those for image pulls. Naming a secret that does not exist lets terraform apply succeed and then leaves the pods in ImagePullBackOff.

Deploy:

All platforms:

terraform init
terraform plan    # Validates config; most input mistakes fail here, not mid-apply
terraform apply

A single apply installs the per-site Gateway and Let's Encrypt Issuer, wires External Secrets Operator to the site's Secrets Manager bundle, and deploys the XMPro Helm release with its database migration and licensing Jobs. Takes about 8-12 minutes, including certificate issuance.

Note

First deploys are the slowest. Every container image is pulled cold and the database-migration and licensing Jobs run inside the Helm install (timeout 30 minutes). Pods can keep converging for several minutes after terraform apply returns: check kubectl get pods -n <name_suffix> and wait for all products to reach Running before judging a deploy failed.

Adding More Sites to the Same Cluster

This is where the layered model pays off. For each additional site, repeat only layers 2, 3, and (optionally) 4 with a new name_suffix. Each site gets its own namespace, databases, KMS key, DNS subzone, and TLS certificates, fully isolated, sharing only the cluster, controllers, and gateway EIPs. The cluster-wide controllers, External Secrets Operator among them, are reused as-is: no application-layer setting changes between the first site and the tenth.

Enabling the AI Product Later

If you deployed with enable_ai = false and want to add the AI product to an existing site, you do not need to redeploy. Enable it in both layers, in order.

First, layer 2 - this creates the AI database on the existing RDS instance:

# examples/layered/infra/terraform.tfvars
enable_ai = true

cd examples/layered/infra
terraform plan
terraform apply
terraform output -raw ai_database_name

Then layer 3, passing the database name the infra layer just reported:

# examples/layered/app/terraform.tfvars
enable_ai        = true
ai_database_name = "XMPro_AI_yourco"

cd ../app
terraform plan
terraform apply

The apply adds the AI deployment, its database-migration Job and an ai. HTTPRoute. Takes about 5-8 minutes. Confirm with kubectl get pods -n <name_suffix> and browse to https://ai.<your-site-zone>/.

Note

The AI product's RAG features (Milvus, Neo4j, TimescaleDB, MQTT) are a separate stack deployed from the infra-ai layer and are not enabled by enable_ai alone. See the module README for the RAG stack.

Need Help?

Common Issues

terraform: command not found → Terraform isn't installed yet. Go back to step 1.

Unable to locate credentials → Run aws configure (or aws sso login) and re-run terraform.

Layer 1 fails on its first resource with VpcLimitExceeded → Error: creating EC2 VPC: operation error EC2: CreateVpc, api error VpcLimitExceeded: The maximum number of VPCs has been reached. The account has hit its VPCs per Region quota (5 by default) in that region. Delete an unused VPC, pick another region, or request a quota increase - and confirm the request reads APPROVED before re-applying, because aws service-quotas get-service-quota reports the requested value while the request is still pending. See Prerequisites.

Node groups fail with Instances failed to join the kubernetes cluster → The greenfield phase-1 apply didn't include the VPC. Re-run phase 1 with both targets (-target=module.cluster.module.vpc -target=module.cluster.module.eks_cluster) so the NAT gateways exist and nodes have egress to ECR.

Certificates stuck at READY=False → DNS isn't resolving yet, or a first order backed off. Verify dig ad.<site-zone> +short (Windows: Resolve-DnsName ad.<site-zone> -Type A) returns the gateway EIPs. If you just delegated the zone, wait for propagation, then kubectl delete certificate xmpro-le-tls -n <name_suffix> and re-apply to clear the backoff.

Second site's certificate never issues; its Gateway reports HostnameConflict on the port-80 listener → Under merged gateways, every site's HTTP listener needs a unique hostname: a hostname-less :80 listener collides with the first site's and its ACME HTTP-01 challenges return 404, leaving SM/IS waiting on the missing xmpro-le-tls Secret. Current module versions set the per-site hostname automatically; if kubectl describe gateway -n <name_suffix> shows HostnameConflict, update to the current module version.

ExternalSecret stuck at SecretSyncedError with AccessDeniedException: Access to KMS is not allowed → The cluster-wide External Secrets Operator role needs kms:Decrypt on each site's own KMS key. The application layer creates that grant for you; if it is missing or has been revoked, xmpro-secrets never materializes and the dbmigrate pre-install hook times out. Restore the grant and force a resync (the default refresh interval is 1 hour):

aws kms create-grant --key-id <site-kms-key-arn> \
  --grantee-principal <shared-eso-role-arn> --operations Decrypt DescribeKey
kubectl annotate externalsecret xmpro-secrets -n <name_suffix> \
  force-sync=$(date +%s) --overwrite

The app layer times out and rolls back; a product pod was Pending with FailedScheduling ... Insufficient memory → The application node group is too small for the install. The database-migration and licensing Jobs run alongside the products, and with Istio injection on every one of those pods carries a sidecar, so the install peak is well above the steady-state total. The Helm release is atomic, so one unschedulable pod rolls the whole site back. Resize the node group (aws eks update-nodegroup-config) and re-apply - see the Sizing Guideline.

terraform plan on the app layer fails before creating anything, mentioning product IDs or keys → is_evaluation_mode is missing from your terraform.tfvars and defaults to false, which requires you to supply every product ID and key. Add is_evaluation_mode = true and re-run. See Step 8.

terraform apply failed partway through → This is normal and recoverable: Terraform records everything it already created, so re-running terraform apply continues from where it stopped rather than starting over. Fix the error it reported first. Two rules: do not delete the terraform.tfstate file, and do not manually delete resources in the AWS console - both leave Terraform unable to reconcile what exists. If you want to see what it believes exists so far, run terraform state list.

Pods stuck in ImagePullBackOff → Run kubectl describe pod <pod> -n <name_suffix> and read the pull error at the bottom. Check in this order:

  1. The pull secret exists. kubectl get secret xmpro-registry -n <name_suffix>. If it is missing, registry_username and registry_password were not set in the application layer. A secret named in image_pull_secrets that does not exist, or is not of type kubernetes.io/dockerconfigjson, produces the same error.
  2. The PAT is valid and scoped. It needs read:packages and must not have expired. Re-run the step 3 preflight to confirm.
  3. The tag exists. A wrong image_tag or a mistyped image_registry produces the same symptom. Compare against docker manifest inspect {{ACR_URL}}/ad:{{VERSION}}.
  4. The nodes can reach the registry. Egress restrictions on the cluster will block the pull regardless of credentials.

terraform destroy on the cluster layer fails with DependencyViolation on the VPC → Kubernetes controllers create AWS resources (NLBs, security groups) outside Terraform state. Destroy the app layer first so they clean up in-band; re-run the cluster destroy if stragglers remain.

Cleanup

Tearing down one site (keeping the cluster):

# Reverse order: stream-hosts → app → infra, for that site only
# Stream Hosts (only if you deployed them) live in the site-template tree:
(cd environments/site-template/stream-hosts && terraform destroy)
cd examples/layered/app   && terraform destroy
cd ../infra               && terraform destroy

The cluster and its controllers stay available for the remaining sites.

Tearing down everything:

(cd environments/site-template/stream-hosts && terraform destroy)
cd examples/layered/app   && terraform destroy
cd ../infra               && terraform destroy
cd ../infra-k8s           && terraform destroy
Important

Destroy in the reverse of apply order. The app layer's controllers create AWS resources outside Terraform state: destroying the app layer before the cluster layer lets them clean up in-band. KMS keys enter a 7-day pending-deletion window; cancel with aws kms cancel-key-deletion --key-id <id> if you destroyed by mistake.

Caution

If the app-layer terraform destroy fails partway, most often because the Kubernetes/Helm providers can't reach the cluster API (flaky network, or the cluster was already deleted), it leaves resources orphaned that both keep billing and block redeploying the same name_suffix (name collisions on the next apply). After a failed destroy, sweep these before re-applying or reusing the site name:

  • Gateway NLB + its ENIs (k8s-envoygat-*). These also block the VPC from deleting and the cluster's IRSA from clearing. Delete the load balancer (aws elbv2 delete-load-balancer); its ENIs release within a minute, then the VPC/subnets can be removed.
  • Secrets Manager bundle secret - xmpro/<name_suffix>/secrets; delete with aws secretsmanager delete-secret --force-delete-without-recovery (otherwise the name is held for the recovery window and the redeploy collides).

Leave the irsa-eso-* IAM role and policy alone. External Secrets Operator belongs to the cluster layer, so its role is shared by every site on the cluster and deleting it breaks the sites still running there.

Symptoms you'll see on a redeploy if the sweep is skipped: ResourceExistsException (Secrets Manager) during the app apply, and a VPC stuck Still destroying on its subnets.
