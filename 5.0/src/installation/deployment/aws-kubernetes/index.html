Deploy XMPro on AWS Kubernetes (EKS)

Introduction

Get XMPro running on Amazon Elastic Kubernetes Service (EKS) with Terraform automation. This is the Kubernetes-native AWS deployment for the 5.0 platform.

Deployment uses a three-layer model designed for shared clusters: one EKS cluster (with its platform controllers) can host multiple isolated XMPro sites, each with its own databases, KMS key, DNS subzone, and Helm release. Additional Stream Hosts are deployed through a small fourth layer.

Layer Applied Contains
1 - Cluster (infra-k8s) Once per cluster VPC, EKS cluster, AWS Load Balancer Controller, Envoy Gateway, cert-manager, GatewayClass, pre-allocated gateway NLB EIPs
2 - Site infrastructure (infra) Once per site RDS SQL Server + databases, KMS key, Route53 subzone + wildcard A record
3 - Site application (app) Once per site External Secrets Operator, per-site Gateway + Let's Encrypt Issuer, XMPro Helm release, HTTPRoutes
4 - Stream Hosts (stream-hosts) Per site, as needed One standalone Stream Host per Collection
Note

This guide works on Windows, Mac, and Linux. Windows users should use Command Prompt or PowerShell. The deployment requires terraform, aws, and kubectl on PATH.

Provision Infrastructure Your Own Way?

Note

Infrastructure provisioning is your responsibility. The Terraform module in this guide is provided as an example only and is not officially supported by XMPro. You are responsible for infrastructure configuration, maintenance, and support. See the Deployment Responsibility Matrix for details.

Tip

The example module uses t3.medium (system) and t3.large (app) node instance types and a db.t3.small SQL Server Express RDS by default, suitable for development and evaluation. SQL Server Express has a 10 GB per-database cap; use sqlserver-se or higher for production. See the module README for production sizing.

You can provision the required infrastructure using:

  • The example Terraform module (community-supported)
  • The AWS console (ClickOps)
  • Your organization's infrastructure-as-code tools

If you provision infrastructure yourself, you'll need:

Required Infrastructure (cluster-level):

  • [ ] VPC - Private and public subnets across at least 2 AZs, NAT gateway, internet gateway
  • [ ] EKS cluster - Kubernetes 1.30+ with managed node groups (system + app pools), OIDC provider enabled
  • [ ] AWS Load Balancer Controller - Installed cluster-wide
  • [ ] Envoy Gateway controller + cert-manager - Installed cluster-wide, with a GatewayClass (eg)
  • [ ] Istio (base + istiod + Istio CNI) - Installed cluster-wide, or set enable_istio = false in the application layer. On a self-built cluster the node security group must allow TCP 15017 from the cluster security group (istiod's sidecar-injection webhook): without it every injected pod fails admission with failed calling webhook ... context deadline exceeded
  • [ ] Pre-allocated Elastic IPs - One per public-subnet AZ, adopted by the gateway NLB

Required Infrastructure (per site):

  • [ ] RDS SQL Server - With 3-4 databases (SM, AD, DS, and optionally AI)
  • [ ] KMS key - Customer-managed key the application layer uses to encrypt its Secrets Manager bundle
  • [ ] IRSA (IAM Roles for Service Accounts) role for XMPro pods - Trust policy bound to system:serviceaccount:<site>:xmpro
  • [ ] Container registry pull access - For {{ACR_URL}} (or your own ECR with mirrored images)
  • [ ] Route53 hosted zone (or external DNS) - With a wildcard A record pointing at the gateway EIPs
Note

Autoscale is not currently supported on Kubernetes (it is in development). XMPro's shared-session handling does not yet work correctly behind a load balancer with multiple replicas, so each product runs a single replica and ElastiCache Redis is not used. The create_redis_cache toggle and enable_autoscale flag exist only to back this future capability, leave them off.

Once you've created these resources, you still need Steps 1-3 (install the CLI tools, sign in to AWS, and clone the module for its app layer), then skip ahead to Step 7: Deploy the Site Application Layer and provide the details in your configuration.

Architecture

┌────────────────────────────────────────────────────────────────┐
│  Layer 1 - Cluster (examples/layered/infra-k8s)                │
│  Apply ONCE per cluster                                        │
│  - VPC, subnets, NAT gateway, IGW                              │
│  - EKS cluster + system / app managed node groups, OIDC        │
│  - AWS Load Balancer Controller (cluster-wide)                 │
│  - Envoy Gateway controller + cert-manager (cluster-wide)      │
│  - GatewayClass "eg" + pre-allocated gateway NLB EIPs          │
└────────────────────────────────────────────────────────────────┘
                              │
                              ▼  per site
┌────────────────────────────────────────────────────────────────┐
│  Layer 2 - Site infrastructure (examples/layered/infra)        │
│  Apply once PER SITE                                           │
│  - RDS SQL Server + SM / AD / DS (/ AI) databases              │
│  - KMS key (per-site secret bundle)                            │
│  - Route53 subzone + wildcard A record → gateway EIPs          │
└────────────────────────────────────────────────────────────────┘
                              │
                              ▼  per site
┌────────────────────────────────────────────────────────────────┐
│  Layer 3 - Site application (examples/layered/app)             │
│  Apply once PER SITE                                           │
│  - External Secrets Operator (AWS Secrets Manager → K8s)       │
│  - Per-site Gateway + Let's Encrypt Issuer                     │
│  - XMPro Helm release: SM, IS, AD, DS, optional AI,            │
│    dbmigrate + licenses Jobs                                   │
│  - Gateway API HTTPRoutes per product                          │
└────────────────────────────────────────────────────────────────┘
                              │
                              ▼  per site, as needed
┌────────────────────────────────────────────────────────────────┐
│  Layer 4 - Stream Hosts (site-template/stream-hosts)           │
│  - One standalone Stream Host Helm release per Collection      │
└────────────────────────────────────────────────────────────────┘

Traffic flow: https://{ad,ds,sm,ai}.<site-zone> → NLB (static EIPs) → Envoy Gateway → HTTPRoute → product Service. The sm. hostname is path-split: /identity/* routes to the Identity Server (IS); everything else routes to Subscription Manager (SM).

Prerequisites

You need:

  • An AWS account with permissions for VPC, EKS, EC2, RDS, ElastiCache, IAM, KMS, Secrets Manager, Route53, and CloudWatch
  • A computer with internet access
  • Access to XMPro's container registry ({{ACR_URL}}) with a pull credential

Quick Deployment

1. Install Required Tools

Install these on your computer:

  • Git: Download here
  • Terraform: Download here (>= 1.5)
  • AWS CLI: Download here (v2)
  • kubectl: Download here (1.30+)

Verify they work:

All platforms:

git --version
terraform version
aws --version
kubectl version --client

2. Login to AWS

All platforms:

aws configure              # Long-lived access keys
# OR
aws sso login              # AWS IAM Identity Center / SSO

# Verify
aws sts get-caller-identity
Tip

Terraform automatically uses your AWS CLI credentials. For CI/CD pipelines, prefer OIDC federation over long-lived keys.

3. Get the Deployment Files

Windows (PowerShell):

git clone {{TERRAFORM_EKS_MODULE_URL}}.git terraform-k8s
cd terraform-k8s\terraform-xmpro-eks\examples\layered\infra-k8s
Copy-Item terraform.tfvars.example terraform.tfvars

Windows (Command Prompt):

git clone {{TERRAFORM_EKS_MODULE_URL}}.git terraform-k8s
cd terraform-k8s\terraform-xmpro-eks\examples\layered\infra-k8s
copy terraform.tfvars.example terraform.tfvars

Mac/Linux:

git clone {{TERRAFORM_EKS_MODULE_URL}}.git terraform-k8s
cd terraform-k8s/terraform-xmpro-eks/examples/layered/infra-k8s
cp terraform.tfvars.example terraform.tfvars

At minimum, edit these values in terraform.tfvars:

company_name = "yourco"          # Drives resource and database naming
name_suffix  = "dev"             # Cluster identifier
aws_region   = "us-west-2"       # Your target region

kubernetes_version = "1.33"
vpc_cidr           = "10.40.0.0/16"
single_nat_gateway = true        # One NAT gateway (cheaper); false = one per AZ
Warning

Do not use xmpro as company_name. It collides with a hardcoded XMPro company in the SM database migration scripts (case-insensitive unique constraint).

4. Deploy Layer 1 - Cluster

The cluster layer configures Kubernetes/Helm providers from the EKS cluster it creates, so a first (greenfield) apply must be done in two phases: create the VPC and cluster first, then apply the rest (the platform controllers, which need a reachable cluster):

All platforms:

terraform init

# Phase 1 - VPC + EKS cluster (so the k8s/helm providers can connect)
terraform apply -target=module.cluster.module.vpc -target=module.cluster.module.eks_cluster

# Phase 2 - platform controllers, GatewayClass, gateway EIPs
terraform apply
Important

Phase 1 must target module.cluster.module.vpc as well as the cluster. Targeting only the cluster prunes the NAT gateways/public subnets from the plan: nodes then come up with no egress to ECR, can't pull the CNI image, and fail to join (NodeGroup CREATE_FAILED: "Instances failed to join the kubernetes cluster").

This creates the VPC, EKS cluster, AWS Load Balancer Controller, Envoy Gateway, cert-manager, Istio (base + istiod + Istio CNI, with the shared gateway joined to the mesh), the GatewayClass, and the pre-allocated gateway EIPs. Takes about 15-20 minutes. You do this once per cluster, additional sites reuse it.

Point kubectl at the new cluster. Run terraform output and copy the values into the command (later steps reuse them):

All platforms:

terraform output
# Note: cluster_name, eks_cluster_oidc_provider_arn, eks_cluster_oidc_provider_url,
#       vpc_id, private_subnet_ids, public_subnet_ids, node_security_group_id,
#       gateway_class_name, gateway_eip_public_ips, irsa_xmpro_role_arn

Then update kubeconfig using the cluster_name value:

All platforms:

aws eks update-kubeconfig --name eks-yourco-dev --region us-west-2

Mac/Linux (substitute straight from Terraform instead of copy/paste):

aws eks update-kubeconfig --name "$(terraform output -raw cluster_name)" --region us-west-2

5. Deploy Layer 2 - Site Infrastructure

Windows (PowerShell):

cd ..\infra
Copy-Item terraform.tfvars.example terraform.tfvars

Windows (Command Prompt):

cd ..\infra
copy terraform.tfvars.example terraform.tfvars

Mac/Linux:

cd ../infra
cp terraform.tfvars.example terraform.tfvars

Edit terraform.tfvars, reusing the cluster VPC and pointing the wildcard DNS at the gateway EIPs (both from layer 1 outputs):

company_name = "yourco"
name_suffix  = "site1"           # Unique per site on this cluster
aws_region   = "us-west-2"

# Reuse the cluster VPC (from layer 1 outputs) - no new VPC
create_vpc             = false
vpc_id                 = "vpc-xxxxx"
private_subnet_ids     = ["subnet-aaa", "subnet-bbb", "subnet-ccc"]
public_subnet_ids      = ["subnet-ddd", "subnet-eee", "subnet-fff"]
node_security_group_id = "sg-xxxxx"

# --- Database ---
db_admin_username  = "xmadmin"
db_admin_password  = "ChangeMe123!Strong"   # see RDS password rules below
db_engine          = "sqlserver-ex"          # sqlserver-se/-ee for production
db_engine_version  = "15.00"
db_instance_class  = "db.t3.small"

# --- Redis ---
# Redis is only consumed by autoscale, which is NOT currently supported on
# Kubernetes (in development). Leave false - no ElastiCache is provisioned.
create_redis_cache = false

# --- DNS ---
enable_custom_domain = true
dns_zone_name        = "site1.xmpro.yourco.com"
# Wildcard A record (*.site1...) → gateway NLB EIPs (layer 1 gateway_eip_public_ips)
cluster_gateway_eip_public_ips = ["52.x.x.x", "13.x.x.x"]
Important

RDS password rules. RDS rejects the master password if it contains /, @, ", or a space: the apply fails with InvalidParameterValue: MasterUserPassword is not a valid password. Use 8+ printable ASCII characters mixing upper/lower/digit and a symbol from the allowed set (e.g. ! # $ % ^ & * - _). Set the same value in the application layer's db_admin_password (Step 7).

Apply:

terraform init
terraform apply

This creates the site's RDS SQL Server (with the SM, AD, and DS databases), KMS key, and Route53 subzone with the wildcard A record. Takes about 10-15 minutes, RDS is the long pole.

6. Configure DNS Delegation

The site's DNS subzone must be delegated from its parent zone before deploying the application layer: cert-manager's Let's Encrypt HTTP-01 challenge needs the hostnames resolving publicly.

terraform output route53_name_servers

Add an NS record in the parent zone for the subzone pointing at the four nameservers shown:

aws route53 change-resource-record-sets --hosted-zone-id <PARENT_ZONE_ID> --change-batch '{
  "Changes": [{
    "Action": "UPSERT",
    "ResourceRecordSet": {
      "Name": "site1.xmpro.yourco.com", "Type": "NS", "TTL": 300,
      "ResourceRecords": [{"Value": "ns-1.awsdns-00.org"}, {"Value": "ns-2.awsdns-00.com"}, {"Value": "ns-3.awsdns-00.co.uk"}, {"Value": "ns-4.awsdns-00.net"}]
    }
  }]
}'
Important

Wait for the delegation to propagate before applying the app layer. A freshly-delegated zone can take a few minutes to resolve from all of Let's Encrypt's validation vantage points: applying too early can make the first certificate order fail a challenge, after which cert-manager backs off (up to ~1 hour) before retrying. Recovery is to kubectl delete certificate xmpro-le-tls -n <name_suffix> and re-apply.

Verify before continuing:

Windows (PowerShell):

Resolve-DnsName ad.site1.xmpro.yourco.com -Type A    # Should return the gateway EIPs

Mac/Linux:

dig ad.site1.xmpro.yourco.com +short    # Should return the gateway EIPs

Using an external provider (GoDaddy, Cloudflare, etc.): set enable_custom_domain = false in layer 2 and create A records for ad., ds., sm. (and ai. if enabled) directly against the gateway EIPs (terraform output gateway_eip_public_ips from layer 1).

7. Deploy the Site Application Layer

Windows (PowerShell):

cd ..\app
Copy-Item terraform.tfvars.example terraform.tfvars

Windows (Command Prompt):

cd ..\app
copy terraform.tfvars.example terraform.tfvars

Mac/Linux:

cd ../app
cp terraform.tfvars.example terraform.tfvars

Edit terraform.tfvars with values from layers 1 and 2:

aws_region   = "us-west-2"
company_name = "yourco"
name_suffix  = "site1"

# [from layer 1]
cluster_name          = "eks-yourco-dev"
irsa_xmpro_role_arn       = "arn:aws:iam::<account>:role/irsa-xmpro-yourco-site1"
cluster_oidc_provider_arn = "arn:aws:iam::<account>:oidc-provider/oidc.eks.us-west-2.amazonaws.com/id/<id>"
cluster_oidc_provider_url = "https://oidc.eks.us-west-2.amazonaws.com/id/<id>"
gateway_class_name        = "eg"     # [from layer 1] gateway_class_name

# [from layer 2]
rds_endpoint        = "rds-yourco-site1.<id>.us-west-2.rds.amazonaws.com"
rds_port            = 1433
ad_database_name    = "XMPro_AD_yourco"
ds_database_name    = "XMPro_DS_yourco"
sm_database_name    = "XMPro_SM_yourco"
ai_database_name    = ""             # from layer 2 output if enable_ai = true
secrets_kms_key_arn = "arn:aws:kms:us-west-2:<account>:key/<id>"
route53_zone_id     = "Z0000000000000000"

# --- RDS master credentials (must match the layer-2 tfvars) ---
db_admin_username = "xmadmin"
db_admin_password = "ChangeMe123!Strong"

# External Secrets Operator: a single-site deploy lets the app layer install ESO.
# On a shared cluster, set true after the first site and reuse the cluster role.
eso_already_installed = false

# --- Container images ---
image_registry     = "{{ACR_URL}}"
image_tag          = "{{VERSION}}"
image_pull_secrets = []             # ["xmpro-registry"] when pulling from a private registry

# --- Company admin (passwords are generated into the secret bundle) ---
# email is a contact address only; the login username is derived separately (see below)
company_admin_first_name    = "Admin"
company_admin_last_name     = "User"
company_admin_email_address = "admin.user@yourco.com"

# --- Licensing (defaults to evaluation product IDs when product vars are empty) ---
enable_licenses = true

# --- Ingress / DNS / TLS ---
enable_custom_domain = true
dns_zone_name        = "site1.xmpro.yourco.com"
letsencrypt_email    = "ops@yourco.com"

# --- Features ---
enable_ai        = false
enable_autoscale = false           # leave false - autoscale is not currently supported on Kubernetes (in development)

# --- Service mesh + Pod Security (defaults shown) ---
enable_istio              = true
istio_peer_authentication = "PERMISSIVE"   # STRICT = enforced in-cluster mTLS
pod_security_standard     = "baseline"
pod_security_enforce      = "baseline"
Important

enable_istio = true requires the cluster layer's Istio install: on a cluster without Istio set it false, or the apply fails on the PeerAuthentication CRD. STRICT requires the shared gateway inside the mesh (the cluster layer meshes it by default); an unmeshed gateway with STRICT refuses all ingress to the site.

Note

The application reads every credential from one aggregate AWS Secrets Manager bundle (xmpro/<name_suffix>/secrets), which External Secrets Operator materializes into the cluster as the xmpro-secrets Kubernetes Secret. There are no separate per-credential bundles.

Deploy:

All platforms:

terraform init
terraform plan    # Validates config; most input mistakes fail here, not mid-apply
terraform apply

A single apply installs the per-site Gateway and Let's Encrypt Issuer, wires External Secrets Operator to the site's Secrets Manager bundle, and deploys the XMPro Helm release with its database migration and licensing Jobs. Takes about 8-12 minutes, including certificate issuance.

Note

First deploys are the slowest. Every container image is pulled cold and the database-migration and licensing Jobs run inside the Helm install (timeout 30 minutes). Pods can keep converging for several minutes after terraform apply returns: check kubectl get pods -n <name_suffix> and wait for all products to reach Running before judging a deploy failed.

8. Access XMPro

All platforms:

kubectl get pods -n site1            # All pods Running
kubectl get certificate -n site1     # READY=True
kubectl get httproute -n site1

Smoke-test the gateway:

Mac/Linux:

curl -s -o /dev/null -w "%{http_code}" https://ad.site1.xmpro.yourco.com/
# 302 = healthy (redirect to login)

Windows (PowerShell):

curl.exe -s -o /dev/null -w "%{http_code}" https://ad.site1.xmpro.yourco.com/
# 302 = healthy (redirect to login)

The company admin password is generated at deploy time and stored in the aggregate Secrets Manager bundle. Retrieve it:

aws secretsmanager get-secret-value \
  --secret-id xmpro/site1/secrets \
  --query SecretString --output text | jq '."xmpro-company-admin-password", ."xmpro-site-admin-password"'

Login at https://sm.<your-site-zone>/:

Account Type Username Password Purpose
Company Admin admin.user@yourco.onxmpro.com xmpro-company-admin-password from the bundle Company management, normal operations
Site Admin admin@xmpro.onxmpro.com xmpro-site-admin-password from the bundle Full system access, license management
Note

The company-admin username is built from your company_admin_first_name, company_admin_last_name, and company_name values as firstname.lastname@<company_name>.onxmpro.com.

9. (Optional) Deploy Stream Hosts

The application layer installs no default in-cluster Stream Host. Deploy Stream Hosts through the dedicated fourth layer: one Helm release per Collection, each with its own collection id and secret.

Mac/Linux:

# Stream Hosts live in the site-template tree, not examples/layered
cd ../../../environments/site-template/stream-hosts
cp template.tfvars.example terraform.tfvars

aws_region                = "us-west-2"
name_suffix               = "site1"
cluster_name          = "eks-yourco-dev"
namespace                 = "site1"
secrets_kms_key_arn       = "arn:aws:kms:us-west-2:<account>:key/<id>"   # layer 2
cluster_secret_store_name = "aws-secrets-site1"                          # from the app layer's ESO
image_registry            = "{{ACR_URL}}"
image_tag                 = "{{VERSION}}"
ds_server_url             = "https://ds.site1.xmpro.yourco.com/"

stream_hosts = {
  default = {
    collection_id    = "<collection-id-from-DS>"
    collection_secret = "<collection-secret>"
    gateway_name     = "SH-EKS-site1"
  }
}

terraform init
terraform apply

Confirm the Stream Host shows online in DS → Stream Hosts.

Adding More Sites to the Same Cluster

This is where the layered model pays off. For each additional site, repeat only layers 2, 3, and (optionally) 4 with a new name_suffix. Each site gets its own namespace, databases, KMS key, DNS subzone, and TLS certificates, fully isolated, sharing only the cluster, controllers, and gateway EIPs. On a shared cluster set eso_already_installed = true in the app layer after the first site.

Need Help?

Common Issues

terraform: command not found → Terraform isn't installed yet. Go back to step 1.

Unable to locate credentials → Run aws configure (or aws sso login) and re-run terraform.

Node groups fail with Instances failed to join the kubernetes cluster → The greenfield phase-1 apply didn't include the VPC. Re-run phase 1 with both targets (-target=module.cluster.module.vpc -target=module.cluster.module.eks_cluster) so the NAT gateways exist and nodes have egress to ECR.

Certificates stuck at READY=False → DNS isn't resolving yet, or a first order backed off. Verify dig ad.<site-zone> +short (Windows: Resolve-DnsName ad.<site-zone> -Type A) returns the gateway EIPs. If you just delegated the zone, wait for propagation, then kubectl delete certificate xmpro-le-tls -n <name_suffix> and re-apply to clear the backoff.

Second site's certificate never issues; its Gateway reports HostnameConflict on the port-80 listener → Under merged gateways, every site's HTTP listener needs a unique hostname: a hostname-less :80 listener collides with the first site's and its ACME HTTP-01 challenges return 404, leaving SM/IS waiting on the missing xmpro-le-tls Secret. Current module versions set the per-site hostname automatically; if kubectl describe gateway -n <name_suffix> shows HostnameConflict, update to the current module version.

ExternalSecret stuck at SecretSyncedError with AccessDeniedException: Access to KMS is not allowed → When adding a site that reuses the shared ESO install (eso_already_installed = true), the shared ESO role has no decrypt access on the new site's KMS key, so xmpro-secrets never materializes and the dbmigrate pre-install hook times out. Grant it and force a resync (the default refresh interval is 1 hour):

aws kms create-grant --key-id <site-kms-key-arn> \
  --grantee-principal <shared-eso-role-arn> --operations Decrypt DescribeKey
kubectl annotate externalsecret xmpro-secrets -n <name_suffix> \
  force-sync=$(date +%s) --overwrite

Pods stuck in ImagePullBackOff → The registry pull Secret hasn't been materialized. Confirm image_pull_secrets and the registry credentials in the secret bundle, and check kubectl get externalsecret -n <name_suffix>.

terraform destroy on the cluster layer fails with DependencyViolation on the VPC → Kubernetes controllers create AWS resources (NLBs, security groups) outside Terraform state. Destroy the app layer first so they clean up in-band; re-run the cluster destroy if stragglers remain.

Cleanup

Tearing down one site (keeping the cluster):

# Reverse order: stream-hosts → app → infra, for that site only
# Stream Hosts (only if you deployed them) live in the site-template tree:
(cd environments/site-template/stream-hosts && terraform destroy)
cd examples/layered/app   && terraform destroy
cd ../infra               && terraform destroy

The cluster and its controllers stay available for the remaining sites.

Tearing down everything:

(cd environments/site-template/stream-hosts && terraform destroy)
cd examples/layered/app   && terraform destroy
cd ../infra               && terraform destroy
cd ../infra-k8s           && terraform destroy
Important

Destroy in the reverse of apply order. The app layer's controllers create AWS resources outside Terraform state: destroying the app layer before the cluster layer lets them clean up in-band. KMS keys enter a 7-day pending-deletion window; cancel with aws kms cancel-key-deletion --key-id <id> if you destroyed by mistake.

Caution

If the app-layer terraform destroy fails partway, most often because the Kubernetes/Helm providers can't reach the cluster API (flaky network, or the cluster was already deleted), it leaves resources orphaned that both keep billing and block redeploying the same name_suffix (name collisions on the next apply). After a failed destroy, sweep these before re-applying or reusing the site name:

  • Gateway NLB + its ENIs (k8s-envoygat-*). These also block the VPC from deleting and the cluster's IRSA from clearing. Delete the load balancer (aws elbv2 delete-load-balancer); its ENIs release within a minute, then the VPC/subnets can be removed.
  • External Secrets IAM role + policy - irsa-eso-<name_suffix> and irsa-eso-<name_suffix>-secrets-read (detach the policy, then delete both).
  • Secrets Manager bundle secret - xmpro/<name_suffix>/secrets; delete with aws secretsmanager delete-secret --force-delete-without-recovery (otherwise the name is held for the recovery window and the redeploy collides). Symptoms you'll see on a redeploy if the sweep is skipped: EntityAlreadyExists (IAM role/policy) and ResourceExistsException (Secrets Manager) during the app apply, and a VPC stuck Still destroying on its subnets.
