Sizing Guideline

This guide provides recommendations for sizing an XMPro deployment on Azure Kubernetes Service (AKS): how large to make the cluster's node pools and how to size the databases. For the Azure App Service (4.x) deployment model, see the App Service Sizing Guideline.

Overview

Small, medium, and large sizing estimates are provided. The small option starts with the minimum recommended resources and, generally, each subsequent size doubles the number of CPU cores and available RAM. Not all components experience the same increase in load, so the estimates may not increase at the same rate for all components.

Many factors influence the number of Apps and Data Streams a deployment can effectively run. These factors include:

  • the number of data streams,
  • how frequently the streams process data,
  • the size of the data payload,
  • the number of recommendations to be monitored,
  • the number of apps and event boards being served,
  • the complexity of apps and event boards (the number of elements and integration points),
  • and the number of concurrent users accessing the apps and event boards.

As a rough guide, an example workload for a Medium-sized deployment would be:

  • ~200 Data Streams running across
  • ~15 Stream Hosts,
  • serving data and triggering recommendations for ~10 Apps

Node Pool Sizing

On Kubernetes, XMPro sizing means two things: making sure the cluster's node pools have enough capacity for the product containers, and sizing the databases (covered in Database Sizing below). The example AKS Terraform module ships with evaluation-grade defaults (a single small system node, a single small application node, and a small shared database), sized for demos, trials, and development, not production load. The variables below are how you scale up from there.

Two Kubernetes terms are used throughout this section:

  • A request is the amount of CPU or memory the Kubernetes scheduler reserves for a container. A node must have at least this much unreserved capacity free before a pod can be placed on it.
  • A limit is the ceiling a container may consume. A container that exceeds its memory limit is terminated (OOM-killed); the XMPro chart deliberately sets memory limits but no CPU limits, so .NET startup is not CPU-throttled.

Requests drive scheduling (can the pod fit?); limits drive worst-case sizing (how much can everything consume at once?). The node pools need capacity for both.

Node pools

An AKS deployment runs two node pools: a system pool that hosts cluster-critical add-ons (CoreDNS, metrics-server, and the AKS management components) and an application pool that hosts the XMPro product pods. Sizing the application pool means giving its nodes enough allocatable capacity for the sum of the product container requests, with headroom for the products to grow toward their limits under load.

Per-product resource requests and limits

The table below lists the CPU and memory each XMPro product container reserves (request) and its memory ceiling (limit), taken from the Helm chart defaults. There are no CPU limits by design. These are the same chart resources regardless of whether you run on AKS or EKS. Stream Host (SH), App Designer (AD), and Data Stream Designer (DS) are enabled by default; on a deployed site the application layer also always deploys Subscription Manager (SM) and Identity Server (IS). The AI product is optional.

Product CPU request Memory request Memory limit
Subscription Manager (SM) 100m 512Mi 1Gi
Identity Server (IS) 100m 1Gi 2Gi
App Designer (AD) 150m 1Gi 4Gi
Data Stream Designer (DS) 150m 2Gi 4Gi
Stream Host (SH) 25m 256Mi 512Mi
Total (SM+IS+AD+DS+SH) 525m ~4.75Gi ~11.5Gi
AI (optional, adds) 25m 384Mi 768Mi

Enabling AI raises the standard totals to roughly 550m CPU request, ~5.1Gi memory request, and ~12.25Gi memory limit.

Note

Database-migration and licensing steps (ad-dbmigrate, ds-dbmigrate, sm-dbmigrate, ai-dbmigrate, licenses) run as short-lived Helm Jobs during install, each requesting 100m CPU / 256Mi and capped at 200m CPU / 512Mi. They finish before the products reach steady state, so they do not count toward the always-on total above, but the application pool must have room to schedule them during the initial deploy.

Translating requests into node size and count

Node capacity is not the same as the VM's advertised size. Kubernetes reserves some of every node's CPU and memory for the kubelet and system processes; what remains is the node's allocatable capacity: the portion actually available to pods. A node advertised as 8 GiB does not offer a full 8 GiB to workloads.

To choose app_node_vm_size and app_node_count:

  1. Start from the request total above (~525m CPU, ~4.75Gi memory for the standard product set; ~550m / ~5.1Gi with AI).
  2. Look up the vCPU and RAM of a candidate VM SKU in the Azure VM sizes documentation, then subtract the AKS system reservation to get its allocatable capacity.
  3. Because the product memory limits (~11.5Gi combined) are far higher than the memory requests, memory pressure under real load, not the request total, is what sizes a production pool. Size the application nodes toward the limit envelope, and confirm the true figure by measuring actual pod memory usage under representative load rather than trusting a static estimate.
  4. Set app_node_count (or enable the cluster autoscaler) so the pool's combined allocatable capacity comfortably exceeds the workload, with headroom for node maintenance and pod rescheduling.

The defaults are a single application node and a single system node, which is why they are evaluation-grade: neither pool has redundancy. For production, run at least two system nodes (so CoreDNS and metrics-server survive a node loss) and size the application pool to your measured load.

All node-pool sizing lives in the AKS module's cluster layer (infra-k8s, deployed once per cluster). The table introduces each variable and its default.

AI and RAG node pool

When the AI product's RAG feature is enabled, its backing services (Milvus vector store, Neo4j graph database, TimescaleDB, and the Mosquitto MQTT broker) run on a dedicated node pool provisioned by the optional AI infrastructure layer (infra-ai), applied once per cluster and shared by all sites. These services are memory-heavy, which is why they get their own pool rather than sharing the application nodes.

The pool is sized by two variables in infra-ai, both larger than the application-pool defaults to accommodate the vector and graph workloads.

Variable Default Controls
ai_node_vm_size Standard_E4as_v5 VM SKU for the dedicated AI pool
ai_node_count 1 AI pool node count

AI persistent volumes use the managed-csi-premium storage class by default (storage_class_name). Size this pool against the data volume you intend to embed and index; the single-node default is an evaluation starting point, not a production figure.

Scaling out

Beyond making nodes bigger, XMPro can scale horizontally by running more replicas of a product, but this requires shared-state coordination. The application layer (app) exposes enable_autoscale (default false), which turns on Redis-backed distributed caching so multiple replicas can coordinate; per-product replica counts (ad_replica_count, ds_replica_count, sm_replica_count, and so on) default to 1, and enforce_single_replica (default false) hard-blocks any product from exceeding one replica when set. At the cluster level, app_autoscaling_enabled turns on the AKS cluster autoscaler to add and remove application nodes automatically within the app_min_count/app_max_count bounds. Note that per-product Horizontal Pod Autoscalers (HPAs) are still a chart follow-up (the chart's HPA template is currently a single-target stub), so horizontal scaling today means setting replica counts explicitly rather than relying on CPU-driven autoscaling of the pods themselves.

Elastic pool default

Rather than giving each database its own SKU, the AKS module places the SM, AD, and DS databases in a shared Standard elastic pool by default (db_use_elastic_pool = true, db_elastic_pool_edtu = 50). An elastic pool lets any single database burst to the full pool capacity while total spend stays capped, a good fit when the databases have uneven, bursty load. The default 50 eDTU pool sits between the Small and Medium per-database estimates above once shared across three databases.

For production sizing you have two levers, both in the site infrastructure layer (infra):

  • Keep the pool, raise its capacity - increase db_elastic_pool_edtu (e.g. to 100 or higher) so the shared budget matches your Medium/Large workload.
  • Switch to standalone databases - set db_use_elastic_pool = false and set db_sku_name (default S0) to the per-database tier from the table above. Use this when you want a guaranteed, isolated allocation per database rather than a shared burst budget.

db_max_size_gb (default 2) caps each database's storage and should be raised for production data volumes.
