Deploy XMPro on Azure Kubernetes Service (AKS)

Introduction

Get XMPro running on Azure Kubernetes Service (AKS) with Terraform automation. This is the Kubernetes-native Azure deployment for the 5.0 platform — distinct from the Azure App Service deployment, which remains available for customers staying on the App Service architecture.

Deployment uses a three-layer model designed for shared clusters: one AKS cluster (with its platform controllers) can host multiple isolated XMPro sites, each with its own databases, Key Vault, DNS subzone, and Helm release.

Layer Applied Contains
1 — Cluster (infra-k8s) Once per cluster AKS cluster, VNet, Envoy Gateway, cert-manager, Log Analytics, shared gateway Public IP
2 — Site infrastructure (infra) Once per site Key Vault, DNS subzone, SQL Server + databases, DNS A record
3 — Site application (app) Once per site External Secrets Operator wiring, per-site Gateway + Issuer, XMPro Helm release, HTTPRoutes
Note

This guide works on Windows, Mac, and Linux. Windows users should use Command Prompt or PowerShell. The deployment requires terraform, az, and kubectl on PATH.

Provision Infrastructure Your Own Way?

Note

Infrastructure provisioning is your responsibility. The Terraform module in this guide is provided as an example only and is not officially supported by XMPro. You are responsible for infrastructure configuration, maintenance, and support. See the Deployment Responsibility Matrix for details.

Tip

The example module uses Standard_B2s_v2 node SKUs and an S0 Azure SQL Database by default — suitable for development and evaluation. For production, override app_node_vm_size, app_node_count, aks_sku_tier, and db_sku_name in your tfvars.

You can provision the required infrastructure using:

  • The example Terraform module (community-supported)
  • Azure Portal (ClickOps)
  • Your organization's infrastructure-as-code tools

If you provision infrastructure yourself, you'll need:

Required Infrastructure (cluster-level):

  • [ ] AKS cluster - Kubernetes 1.30+ with system + app node pools, OIDC issuer enabled
  • [ ] Envoy Gateway controller - Installed cluster-wide (envoy-gateway-system namespace)
  • [ ] cert-manager - Installed cluster-wide with Gateway API support enabled (config.enableGatewayAPI=true)
  • [ ] Istio (base + istiod) - Installed cluster-wide, or set enable_istio = false in the application layer
  • [ ] Static Public IP - In the node resource group, used by the gateway service

Required Infrastructure (per site):

  • [ ] Key Vault - For application secrets, consumed by External Secrets Operator
  • [ ] Azure SQL Server - With 3-4 databases (SM, AD, DS, and optionally AI)
  • [ ] Container registry pull credential - For {{ACR_URL}} (or your own ACR with mirrored images)
  • [ ] DNS zone or subzone - With an A record pointing at the gateway Public IP

Once you've created these resources, skip to Step 7: Deploy the Site Application Layer and provide the details in your configuration.

Architecture

┌────────────────────────────────────────────────────────────────┐
│  Layer 1 — Cluster (examples/layered/infra-k8s)                │
│  Apply ONCE per cluster                                        │
│  - AKS cluster + system / app node pools, OIDC issuer          │
│  - VNet + AKS subnet                                           │
│  - Envoy Gateway controller (cluster-wide)                     │
│  - cert-manager with Gateway API support (cluster-wide)        │
│  - Log Analytics + Application Insights                        │
│  - Static gateway Public IP (shared by all sites)              │
└────────────────────────────────────────────────────────────────┘
                              │
                              ▼  per site
┌────────────────────────────────────────────────────────────────┐
│  Layer 2 — Site infrastructure (examples/layered/infra)        │
│  Apply once PER SITE                                           │
│  - Key Vault (per-site secrets)                                │
│  - SQL Server + SM / AD / DS (/ AI) databases                  │
│  - DNS subzone + wildcard A record → gateway Public IP         │
└────────────────────────────────────────────────────────────────┘
                              │
                              ▼  per site
┌────────────────────────────────────────────────────────────────┐
│  Layer 3 — Site application (examples/layered/app)             │
│  Apply once PER SITE                                           │
│  - External Secrets Operator (installed once, reused per site) │
│  - Per-site Gateway + Let's Encrypt Issuer                     │
│  - XMPro Helm release: SM2, IS, AD, DS, optional AI,           │
│    Stream Host, dbmigrate + licenses Jobs                      │
│  - Gateway API HTTPRoutes per product                          │
└────────────────────────────────────────────────────────────────┘

Traffic flow: https://{ad,ds,sm,ai}.<site-zone> → gateway Public IP → Envoy Gateway → HTTPRoute → product Service. The sm. hostname is path-split: /identity/* routes to the Identity Server (IS); everything else routes to Subscription Manager (SM2).

Prerequisites

You need:

  • An Azure subscription with Contributor (or equivalent) role
  • A computer with internet access
  • Access to XMPro's container registry ({{ACR_URL}}) with a pull credential

Quick Deployment

1. Install Required Tools

Install these on your computer:

  • Git: Download here
  • Terraform: Download here (>= 1.5)
  • Azure CLI: Download here (>= 2.50)
  • kubectl: Download here (1.30+)

Verify they work:

All platforms:

git --version
terraform version
az version
kubectl version --client

2. Login to Azure

All platforms:

az login
az account set --subscription "YOUR-SUBSCRIPTION-NAME-OR-ID"
az account show
Tip

Terraform automatically uses your Azure CLI credentials. For CI/CD pipelines, use OIDC workload identity federation (ARM_USE_OIDC=true) or a service principal via ARM_CLIENT_ID / ARM_CLIENT_SECRET environment variables.

3. Get the Deployment Files

Windows (PowerShell):

git clone https://github.com/XMPro/terraform-xmpro-aks.git
cd terraform-xmpro-aks\examples\layered\infra-k8s
Copy-Item terraform.tfvars.example terraform.tfvars

Windows (Command Prompt):

git clone https://github.com/XMPro/terraform-xmpro-aks.git
cd terraform-xmpro-aks\examples\layered\infra-k8s
copy terraform.tfvars.example terraform.tfvars

Mac/Linux:

git clone https://github.com/XMPro/terraform-xmpro-aks.git
cd terraform-xmpro-aks/examples/layered/infra-k8s
cp terraform.tfvars.example terraform.tfvars

At minimum, edit these values in terraform.tfvars:

subscription_id = "00000000-0000-0000-0000-000000000000"

company_name = "yourco"          # Drives resource naming
name_suffix  = "dev"             # Cluster identifier
location     = "australiaeast"   # Your target region

kubernetes_version  = "1.33"
system_node_vm_size = "Standard_B2s_v2"
system_node_count   = 1

# Shared by every site on this cluster
gateway_public_ip_name = "pip-gateway-cluster"
Warning

Do not use xmpro as company_name for a site. It collides with a hardcoded XMPro company in the SM database migration scripts (case-insensitive unique constraint).

4. Deploy Layer 1 — Cluster

All platforms:

terraform init
terraform apply   # Type 'yes' when asked

This creates the AKS cluster, VNet, Envoy Gateway, cert-manager, Istio (with the shared gateway joined to the mesh), monitoring, and the shared gateway Public IP. Takes about 10-15 minutes. You only do this once per cluster — additional sites reuse it.

Point kubectl at the new cluster and note the layer outputs:

az aks get-credentials \
  --resource-group $(terraform output -raw resource_group_name) \
  --name $(terraform output -raw cluster_name)

terraform output
# Note: resource_group_name, cluster_name, cluster_pip_ip,
#       gateway_class_name, app_insights_connection_string

5. Deploy Layer 2 — Site Infrastructure

Windows (PowerShell):

cd ..\infra
Copy-Item terraform.tfvars.example terraform.tfvars
$env:TF_VAR_db_admin_password = "ChangeMe123!Strong"

Mac/Linux:

cd ../infra
cp terraform.tfvars.example terraform.tfvars
export TF_VAR_db_admin_password="ChangeMe123!Strong"

Edit terraform.tfvars with the values from layer 1:

subscription_id = "00000000-0000-0000-0000-000000000000"

company_name = "yourco"
name_suffix  = "site1"            # Unique per site on this cluster
location     = "australiaeast"

# [from layer 1] terraform output resource_group_name
cluster_resource_group_name = "rg-aks-yourco-dev"

acr_name = "xmpro"                # Registry providing pull access

# --- DNS ---
enable_custom_domain = true
dns_zone_name        = "site1.xmpro.yourco.com"
# [from layer 1] terraform output cluster_pip_ip
cluster_pip_ip = "20.x.x.x"

# --- Database ---
db_admin_username = "xmadmin"
db_sku_name       = "S0"          # Bump for production
db_max_size_gb    = 2

Apply:

terraform init
terraform apply

This creates the site's Key Vault, DNS subzone (with wildcard A record at the gateway IP), and SQL Server with the SM, AD, and DS databases. Takes about 5 minutes.

6. Configure DNS Delegation

The site's DNS subzone must be delegated from its parent zone before deploying the application layer — cert-manager's Let's Encrypt HTTP-01 challenge needs the hostnames resolving publicly.

terraform output dns_zone_name_servers

Add an NS record in the parent zone for the subzone pointing at the four nameservers shown.

Using Azure DNS for the parent zone:

az network dns record-set ns create \
  --resource-group <parent-zone-rg> --zone-name xmpro.yourco.com \
  --name site1 --ttl 300

for ns in $(terraform output -json dns_zone_name_servers | jq -r '.[]'); do
  az network dns record-set ns add-record \
    --resource-group <parent-zone-rg> --zone-name xmpro.yourco.com \
    --record-set-name site1 --nsdname "$ns"
done

Using an external provider (GoDaddy, Cloudflare, etc.): create the NS records in your provider's console, or skip Azure DNS entirely by setting enable_custom_domain = false in layer 2 and creating A records for ad., ds., sm. (and ai. if enabled) directly against the cluster_pip_ip.

Verify before continuing:

Windows (PowerShell):

Resolve-DnsName ad.site1.xmpro.yourco.com -Type A
# Should return the gateway Public IP

Mac/Linux:

dig ad.site1.xmpro.yourco.com +short
# Should return the gateway Public IP

7. Deploy the Site Application Layer

Windows (PowerShell):

cd ..\app
Copy-Item terraform.tfvars.example terraform.tfvars
$env:TF_VAR_db_admin_password = "ChangeMe123!Strong"
$env:TF_VAR_company_admin_password = "YourCompanyPassword123!"
$env:TF_VAR_site_admin_password = "YourSitePassword123!"

Mac/Linux:

cd ../app
cp terraform.tfvars.example terraform.tfvars
export TF_VAR_db_admin_password="ChangeMe123!Strong"
export TF_VAR_company_admin_password="YourCompanyPassword123!"
export TF_VAR_site_admin_password="YourSitePassword123!"

Edit terraform.tfvars with values from layers 1 and 2:

subscription_id = "00000000-0000-0000-0000-000000000000"

company_name = "yourco"
name_suffix  = "site1"
location     = "australiaeast"

# [from layer 1]
resource_group_name     = "rg-aks-yourco-dev"
cluster_name        = "aks-yourco-dev"
aks_resource_group_name = "rg-aks-yourco-dev"

# [from layer 2]
key_vault_name   = "kv-yourco-site1"
key_vault_id     = "/subscriptions/.../vaults/kv-yourco-site1"
key_vault_uri    = "https://kv-yourco-site1.vault.azure.net/"
sql_server_fqdn  = "sql-aks-yourco-site1.database.windows.net"
ad_database_name = "sqldb-site1-ad"
ds_database_name = "sqldb-site1-ds"
sm_database_name = "sqldb-site1-sm"

# ESO shared-cluster mode: installed once by layer 1, reused per site
eso_already_installed     = true
existing_eso_principal_id = ""   # principal (object) ID of the cluster's ESO managed identity — see note below

# --- Container images ---
image_registry = "{{ACR_URL}}"
image_tag        = "{{VERSION}}"

# --- Company admin ---
company_admin_first_name    = "Admin"
company_admin_last_name     = "User"
company_admin_email_address = "admin.user@yourco.com"

# --- Ingress / DNS / TLS ---
enable_custom_domain = true
dns_zone_name        = "site1.xmpro.yourco.com"
letsencrypt_email    = "ops@yourco.com"
gateway_class_name   = "eg"      # [from layer 1] terraform output gateway_class_name

# --- Features ---
enable_ai                  = false
enable_default_stream_host = true
enable_licenses            = true

# --- Service mesh + Pod Security (defaults shown) ---
enable_istio              = true
istio_peer_authentication = "PERMISSIVE"   # STRICT = enforced in-cluster mTLS
pod_security_standard     = "baseline"     # audit/warn only; no enforce on AKS (no Istio CNI)

# --- Product IDs / Keys ---
# Leave empty for evaluation defaults; supply real values for licensed deployments
# sm_product_id  = ""
# sm_product_key = ""
Important

enable_istio = true requires the cluster layer's Istio install — on a cluster without Istio set it false, or the apply fails on the PeerAuthentication CRD. STRICT requires the shared gateway inside the mesh (the cluster layer meshes it by default); an unmeshed gateway with STRICT refuses all ingress to the site.

Tip

Leaving the product ID/key variables empty pins them to XMPro's public evaluation values — useful for demos and trials without supplying real licence material.

Important

existing_eso_principal_id must be the principal (object) ID of the External Secrets Operator managed identity that was created when ESO was installed on the cluster (layer 1) — for example az identity show -g <cluster-rg> -n <eso-identity-name> --query principalId -o tsv. Do not use the cluster's kubelet identity: ESO authenticates as its own identity, so granting the kubelet identity access to the Key Vault leaves ESO with a 403 ForbiddenByRbac, xmpro-secrets is never created, and the dbmigrate pre-install hook times out (rolling back the whole atomic release).

Deploy:

All platforms:

terraform init
terraform plan    # Validates config; most input mistakes fail here
terraform apply

A single apply installs the per-site Gateway and Let's Encrypt Issuer, wires External Secrets Operator to the site's Key Vault, and deploys the XMPro Helm release with its database migration and licensing Jobs. Takes about 8-12 minutes.

Note

First deploys are the slowest. Every container image is pulled cold and the database-migration and licensing Jobs run inside the Helm install (timeout 30 minutes). Pods can keep converging for several minutes after terraform apply returns — check kubectl get pods -n <name_suffix> and wait for all products to reach Running before judging a deploy failed.

8. Access XMPro

All platforms:

kubectl get pods -n <name_suffix>       # All pods Running
kubectl get certificate -n <name_suffix> # READY=True
kubectl get httproute -n <name_suffix>

# Smoke-test
curl -s -o /dev/null -w "%{http_code}" https://ad.site1.xmpro.yourco.com/
# 302 = healthy (redirect to login)

Login at https://sm.<your-site-zone>/:

Account Type Username Password Purpose
Company Admin admin.user@yourco.onxmpro.com Your company_admin_password Company management, normal operations
Site Admin admin@xmpro.onxmpro.com Your site_admin_password Full system access, license management
Note

The username is built from your company_admin_first_name, company_admin_last_name, and company_name values as firstname.lastname@<company_name>.onxmpro.com.

Adding More Sites to the Same Cluster

This is where the three-layer model pays off. For each additional site, repeat only layers 2 and 3 with a new name_suffix:

# Layer 2 with name_suffix = "site2", dns_zone_name = "site2.xmpro.yourco.com"
# Layer 3 with the matching outputs

Each site gets its own namespace, databases, Key Vault, DNS subzone, and TLS certificates — fully isolated, sharing only the cluster, controllers, and gateway IP.

Need Help?

Common Issues

terraform: command not found → Terraform isn't installed yet. Go back to step 1.

Please run 'az login' from Terraform → Run az login (or az login --use-device-code for headless environments) and re-run terraform.

Cluster authentication failed from kubectl → Refresh kubeconfig: az aks get-credentials --resource-group <rg> --name <aks> --overwrite-existing.

Certificates stuck at READY=False → NS delegation likely missing or not propagated. Verify dig ad.<site-zone> +short (Windows: Resolve-DnsName ad.<site-zone> -Type A) returns the gateway Public IP. Then kubectl describe certificate -n <name_suffix> for the cert-manager error detail.

Pods stuck in ImagePullBackOff → XMPro's registry ({{ACR_URL}}) is anonymous-pull, so this is normally a wrong image_tag, a mistyped image_registry, or nodes that can't reach the registry rather than a credentials problem. Run kubectl describe pod <pod> -n <name_suffix> and read the pull error at the bottom. If you mirror the images to your own authenticated registry, note that the module does not currently wire a pull secret — you would need to create one in the namespace and reference it yourself.

SQL connection failures during the dbmigrate Jobs → Confirm TF_VAR_db_admin_password matched between layers 2 and 3, and that the SQL server's firewall allows Azure services (the example module enables this by default).

Apply takes longer than 30 minutes → First-time cluster apply can take up to 25 minutes if AKS provisions slowly. Check the Azure Portal (Kubernetes services) for progress.

Cleanup

Tearing down one site (keeping the cluster):

# Destroy layer 3 then layer 2 for that site only
cd examples/layered/app   && terraform destroy
cd ../infra               && terraform destroy

The cluster and its controllers stay available for the remaining sites.

Tearing down everything:

# Reverse order of apply: app → infra (per site) → infra-k8s (cluster)
cd examples/layered/app      && terraform destroy
cd ../infra                  && terraform destroy
cd ../infra-k8s              && terraform destroy
Important

Destroy in the reverse of apply order. Destroying the cluster layer while site layers still reference it strands their Terraform state with unreachable resources.

Caution

If the app-layer terraform destroy fails partway — most often because the Kubernetes/Helm providers can't reach the cluster API (flaky network, or the cluster was already deleted) — it leaves resources orphaned that block redeploying the same name_suffix (name collisions on the next apply) and can keep billing. After a failed destroy, sweep the site's leftovers before re-applying or reusing the name: the gateway load balancer / public IP, the External Secrets identity and its role assignment, and the site's Key Vault secrets (the Key Vault or its secrets are held for a soft-delete/purge window — purge them, or the redeploy collides). The pattern is the same one seen on EKS (orphaned gateway LB + ESO identity + secret store after a failed app destroy); confirm the exact Azure resource names for your deployment.
