Migrate from Azure App Service to AKS

If you're currently running XMPro on Azure App Service (the v4.x Azure Terraform or legacy ARM deployment) and planning to move to v5.0 on AKS, this guide walks through a side-by-side migration: deploy the new AKS environment, copy your databases into it, let the schema migration Jobs upgrade them, reconcile them to the new environment, validate, then cut DNS over.

Both environments live in Azure, which makes this the gentlest of the platform migrations — database copies are a single az sql db copy command, and you can even run both environments in the same subscription during the transition.

App Service (v4.x) v5.0 AKS
Compute App Service Plans per product Shared AKS cluster, containers per product
Products SM, AD, DS SM2 + IS (identity split out), AD, DS, optional AI
Database Azure SQL Database Azure SQL Database (new per-site server)
TLS App Service managed certificates Let's Encrypt via cert-manager at Envoy Gateway
Ingress Per-app *.azurewebsites.net + custom domains One gateway Public IP → Envoy Gateway → HTTPRoutes
Secrets Key Vault references in app settings Key Vault + External Secrets Operator
Multi-environment One stack per environment One cluster, many isolated sites
Important

Your data survives the migration. The databases carry everything that matters:

  • All users, roles, companies, and product registrations (SM database)
  • All applications and pages (AD database)
  • All data streams, collections, and stream host registrations (DS database)

The v5.0 database migration Jobs upgrade the schema from 4.x to 5.0 automatically on first deploy against the copied databases.

Caution

The side-by-side approach means your App Service environment keeps running untouched until you've validated the new one. Do not decommission anything until the post-migration validation passes.

Required Information from Your Existing Installation

Document these values from your App Service deployment before starting.

1. Azure Resource Information

Configuration Item Where to Find Example
Resource Group Name Azure Portal rg-yourco-prod
Azure Region Azure Portal australiaeast
SQL Server Name Azure Portal → SQL servers sql-yourco-prod.database.windows.net
SQL Admin Username/Password Key Vault or secure storage sqladmin / (your password)
SM / AD / DS Database Names Azure Portal → SQL databases SM, AD, DS
Current Product URLs App Services → Custom domains https://sm.xmpro.yourco.com
Key Vault Name Azure Portal → Key vaults kv-yourco-prod

2. Application Configuration

Configuration Item Where to Find Example
AD encryption key App Service config xm__xmpro__appDesigner__encryptionKey (or its Key Vault reference) base64 / string
Company Names SM → Companies YourCo
Stream Host Collection IDs/Secrets DS → Collections GUIDs
SMTP Configuration App Service → Configuration Server, port, credentials
Custom Environment Variables App Service → Configuration Any xm__-prefixed settings

Finding values from the Azure CLI:

az resource list --resource-group rg-yourco-prod --output table
az sql db list --resource-group rg-yourco-prod --server sql-yourco-prod --output table
az webapp config appsettings list --resource-group rg-yourco-prod --name app-yourco-sm \
  > sm-appsettings-backup-$(date +%Y%m%d).json

az resource list --resource-group rg-yourco-prod --output table
az sql db list --resource-group rg-yourco-prod --server sql-yourco-prod --output table
az webapp config appsettings list --resource-group rg-yourco-prod --name app-yourco-sm |
  Out-File "sm-appsettings-backup-$(Get-Date -Format yyyyMMdd).json"
Important

Carry over the AD encryption key. XMPro encrypts certain stored values (e.g. data-source connection strings in AD) with the App Designer encryption key. If the v5.0 deployment generates a different key than the App Service environment that wrote the data, those values can't be decrypted after migration. Capture the v4.x xm__xmpro__appDesigner__encryptionKey (above) and supply it to the v5.0 application layer rather than letting it generate a fresh one. DS and AI encryption keys live in their own databases and carry over automatically — only the AD key needs to be supplied.

Backup Before Migrating

Caution

Always back up before migrating. The migration copies your databases — the originals are never modified — but backups are still your recovery path.

1. Export each database to a BACPAC

# Repeat for SM, AD, DS
az sql db export \
  --resource-group rg-yourco-prod \
  --server sql-yourco-prod \
  --name SM \
  --storage-key-type StorageAccessKey \
  --storage-key <your-storage-key> \
  --storage-uri https://<storage-account>.blob.core.windows.net/backups/SM_PreMigration.bacpac \
  --admin-user sqladmin \
  --admin-password <password>

2. Snapshot App Service configuration

for app in app-yourco-sm app-yourco-ad app-yourco-ds; do
  az webapp config appsettings list \
    --resource-group rg-yourco-prod --name $app \
    > ${app}-settings-backup-$(date +%Y%m%d).json
done

foreach ($app in 'app-yourco-sm', 'app-yourco-ad', 'app-yourco-ds') {
  az webapp config appsettings list --resource-group rg-yourco-prod --name $app |
    Out-File "$app-settings-backup-$(Get-Date -Format yyyyMMdd).json"
}

Running the Migration

These steps use the migration4.6 example in the AKS Terraform module. It mirrors the standard layered deployment — layer 1 cluster (infra-k8s), layer 2 site infrastructure (infra), layer 3 application (app) — and adds one extra migration stage that runs after the application layer to reconcile the references your copied databases carried over from the source environment. You supply a few clearly-labelled inputs and run one apply per stage — there is no SQL to write.

The apply order (matching the example's README.md) is:

infra-k8s  →  infra  →  [az sql db copy]  →  app  →  migration

1. Deploy the cluster and site infrastructure

From the migration4.6 example, apply the infra-k8s (cluster) and infra (site infrastructure) stages, following the AKS deployment guide. Each stage ships only a terraform.tfvars.example — copy it to terraform.tfvars and fill in the marked values before applying. Two adjustments for a migration:

Use a temporary DNS subzone for validation — and delegate it before layer 3. Deploy with a staging zone (e.g. staging.xmpro.yourco.com) so the new environment is fully testable while production traffic still flows to App Service. Layer 2 creates the Azure DNS zone, but you must delegate it in the parent zone (add the staging zone's NS records to xmpro.yourco.com, wherever that parent is hosted) before applying layer 3. If the staging hostnames don't resolve, cert-manager's HTTP-01 challenge can't complete, the Let's Encrypt certificate stays pending, and the is/sm2 pods block waiting on the TLS secret.

Layer 2's own databases are not used in a migration. The infra stage creates a SQL server plus fresh empty databases (sqldb-aks-<company>-<site>-sm etc.). You don't touch those — your production databases are copied in under their original names in the next step, and the app and migration stages are then pointed at those names.

Important

Apply the infra-k8s and infra stages, but stop before the app and migration stages. The databases must be copied in before app — otherwise the app stage's dbmigrate Jobs initialize the fresh empty databases instead of upgrading yours.

2. Copy your databases to the new SQL server

Azure SQL supports direct cross-server database copy. The target server admin credentials are the db_admin_username/db_admin_password you set in the infra stage. The copies keep their source names (SM, AD, DS in this guide) — the app and migration stages are pointed at those names in the next steps:

# Copy production databases across, keeping the source names
az sql db copy \
  --resource-group rg-yourco-prod --server sql-yourco-prod --name SM \
  --dest-resource-group <new-rg> --dest-server sql-aks-yourco-site1 --dest-name SM

az sql db copy \
  --resource-group rg-yourco-prod --server sql-yourco-prod --name AD \
  --dest-resource-group <new-rg> --dest-server sql-aks-yourco-site1 --dest-name AD

az sql db copy \
  --resource-group rg-yourco-prod --server sql-yourco-prod --name DS \
  --dest-resource-group <new-rg> --dest-server sql-aks-yourco-site1 --dest-name DS
Note

Cross-server copy requires the servers to be in the same tenant and your identity to have access to both. If the servers are in different tenants or you prefer an offline transfer, use the BACPAC export from the backup step with az sql db import instead.

The copied databases will run under the new server's admin login. Database-scoped users carried over from the source; the dbmigrate Jobs connect with the server admin credentials from your tfvars.

A copied database also inherits the source's SKU and size, not the infra stage's db_sku_name/db_max_size_gb. Because the copies keep their own names, Terraform never manages (or tries to resize) them.

Verify the copies completed:

az sql db list --resource-group <new-rg> --server sql-aks-yourco-site1 --output table
Note

The empty sqldb-aks-* databases the infra stage created stay behind unused in a migration, billing at db_sku_name. They are Terraform-managed, so deleting them manually only lasts until the next infra apply recreates them — keep db_sku_name/db_max_size_gb at the smallest tier to minimise their cost, and remove them when the site is decommissioned.

3. Apply the application stage

Apply the app stage next — before the migration stage. On startup, its dbmigrate Jobs detect the existing 4.x schema in each copied database and upgrade it in place to 5.0 — including the SM schema changes for the SM2/IS split.

Copy app/terraform.tfvars.example to terraform.tfvars — it marks every migration-specific value with a REPLACE_ placeholder — and set:

# The COPIED databases from step 2 (source names)
sm_database_name = "SM"
ad_database_name = "AD"
ds_database_name = "DS"

# Product IDs/keys from the source SM database — dbo.Product (IDs) and
# dbo.ProductKey (keys) — so each deployed product matches its registered
# OIDC client. Enter the IDs in lowercase.
sm_product_id  = "<source SM product id, lowercase>"
sm_product_key = "<source SM product key>"
ad_product_id  = "<source AD product id, lowercase>"
ad_product_key = "<source AD product key>"
ds_product_id  = "<source DS product id, lowercase>"
ds_product_key = "<source DS product key>"

# Carry over the AD encryption key so migrated AD can decrypt its existing
# data-source connection strings. AD reads it at startup and never stores it,
# so it must be set before the first apply. (DS/AI keys live in their own
# databases and carry over automatically — only the AD key is supplied here.)
ad_encryption_key = "<your v4.x xm__xmpro__appDesigner__encryptionKey>"

Query the product IDs and keys from the source SM database (the IDs must be entered in lowercase — 5.0 validates the OIDC audience case-sensitively):

SELECT
    p.Name AS ProductName,
    LOWER(CONVERT(varchar(36), p.Id)) AS ProductId,
    pk.[Key] AS ProductKey
FROM dbo.Product p
JOIN dbo.ProductKey pk ON pk.ProductId = p.Id
WHERE p.Name IN ('SM', 'AD', 'DS')
ORDER BY p.Name;

Extract the AD encryption key from the appsettings snapshot you took in the backup step:

jq -r '.[] | select(.name == "xm__xmpro__appDesigner__encryptionKey") | .value' \
  app-yourco-ad-settings-backup-<date>.json

(Get-Content app-yourco-ad-settings-backup-<date>.json | ConvertFrom-Json) |
  Where-Object name -eq 'xm__xmpro__appDesigner__encryptionKey' |
  Select-Object -ExpandProperty value

Then apply:

cd examples/migration4.6/app
terraform apply

Watch the dbmigrate Jobs complete. The site's Kubernetes namespace is the name_suffix you set in the app stage — site1 throughout this guide:

kubectl get jobs -n site1
kubectl logs -n site1 job/xmpro-sm-dbmigrate --tail=50
kubectl logs -n site1 job/xmpro-ad-dbmigrate --tail=50
kubectl logs -n site1 job/xmpro-ds-dbmigrate --tail=50
Note

Schema migrations are cumulative — the Jobs apply every migration between your source version and 5.0 in sequence. For large databases this takes longer than a fresh install. If a Job hits its backoff limit, check its logs before re-running; contact XMPro support if a specific migration step fails repeatedly.

4. Run the migration stage

With the app deployed, apply the migration stage. It runs a Kubernetes Job that connects to your copied databases and reconciles everything still pointing at the old environment — automatically, with no SQL to write:

  • SM — rewrites each product's Product URL / Log Out URL, and aligns the SM ProductKey row with the key this deployment presents (the sm_product_key you set in step 3)
  • AD — rewrites the server URL reference in XMGlobalSetting
  • DS — rewrites the server URL references in ServerVariables

This is what makes OIDC sign-in to the products succeed instead of failing with "Access Denied".

The stage runs after the app stage and reuses the app's in-cluster secret for the database password (and its image pull secret) — no passwords are entered here. Copy migration/terraform.tfvars.example to terraform.tfvars and set:

sql_server_fqdn   = "<new-sql-server>.database.windows.net"   # from the infra stage
db_admin_username = "xmadmin"

# The COPIED databases from step 2 (source names)
sm_database_name = "SM"
ad_database_name = "AD"
ds_database_name = "DS"

# Must match the app stage's name_suffix — the Job runs in the app's namespace
namespace = "site1"

ad_url = "https://ad.staging.xmpro.yourco.com"
ds_url = "https://ds.staging.xmpro.yourco.com"
# ai_url = "https://ai.staging.xmpro.yourco.com"   # only if AI is deployed

cd examples/migration4.6/migration
terraform apply
Note

The migration stage operates only on your copied databases — it never touches the source environment — and is safe to re-run if you change hostnames. It rewrites only XMPro's own App Designer / Data Stream Designer URL references, leaving any third-party URLs (e.g. cloud-service endpoints) untouched.

Tip

If OIDC sign-in to App Designer or Data Stream Designer still returns "Access Denied" after the migration stage, the most common cause is a hostname that changed after the migration stage ran. Re-apply the migration stage with the corrected hostnames, then restart the affected pods. As a last-resort manual check you can log in to the new SM with your existing admin credentials → menu (☰) → Products and confirm the Product URL / Product Log Out URL for each product match your new hostnames.

5. Upgrade and reconnect Stream Hosts

v4.x stream hosts are not compatible with the v5.0 platform. For each stream host:

  1. Install the v5.0 stream host (download link is surfaced in DS → Stream Hosts)
  2. Configure it with the same Collection ID and Secret as before — these carried over in the DS database, so existing data stream bindings reconnect automatically
  3. Point its server URL at the new DS hostname
  4. Confirm it shows online in the new DS

If your stream hosts run as Azure Container Instances from the App Service deployment, replace them with v5.0 containers (or run the default in-cluster stream host via enable_default_stream_host = true and migrate stream assignments to it).

6. Validate, then cut over DNS

Run the full post-migration validation below against the staging hostnames. When everything passes:

  1. Update your production DNS records (sm., ad., ds.) to point at the new gateway Public IP (or re-deploy layers 2-3 with the production dns_zone_name and delegate it)
  2. Lower the record TTLs ahead of cutover (e.g. 300s) so rollback is fast
  3. After cutover, monitor the new environment for an agreed soak period before decommissioning

Post-Migration Validation

1. Platform health

The Kubernetes namespace is the app stage's name_suffix — site1 throughout this guide:

kubectl get pods -n site1                    # All Running
kubectl get certificate -n site1             # READY=True
curl -s -o /dev/null -w "%{http_code}" https://sm.<zone>/   # 302
curl -s -o /dev/null -w "%{http_code}" https://ad.<zone>/   # 302
curl -s -o /dev/null -w "%{http_code}" https://ds.<zone>/   # 302

2. Data integrity

  • Login with pre-migration credentials — users carried over in the SM database
  • Companies and roles — spot-check in SM that companies, users, and role assignments match the App Service environment
  • Applications — open your most important applications in AD; verify pages render and data connections work
  • Data streams — open existing streams in DS; verify canvases, agent configurations, and run state
  • Stream hosts — all hosts online, streams executing, data flowing end to end

3. Integrations

  • Verify any external systems calling XMPro APIs work against the new hostnames
  • Re-test SMTP (password reset email is a quick end-to-end check)
  • Confirm agents reaching Azure resources (Storage, Event Hubs, etc.) still have network reachability from the AKS VNet

Rollback (if needed)

The App Service environment was never modified, so rollback is a DNS operation:

  1. Revert the DNS records to the App Service targets
  2. Users are back on the old environment within the record TTL
Caution

Any data created in the new environment after cutover lives only in the new databases. If you must roll back after running in production, plan a reverse data reconciliation before re-cutting over — or accept the gap. This is the strongest argument for a generous validation period before decommissioning App Service.

When you're confident in the new environment, decommission the App Service stack with its Terraform (terraform destroy in the legacy configuration) or by deleting the resource group.
