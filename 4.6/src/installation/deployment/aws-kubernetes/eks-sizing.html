Sizing Guideline

Overview

This page explains how the EKS deployment is sized, what the shipped defaults give you, and what to change for a production site. It covers the node groups, the per-product resource requests, and the RDS instance.

The defaults in the example Terraform module target development and evaluation. They are deliberately small and cheap. Do not run a production site on them without reading the production notes below.

Two terms used throughout:

  • A request is the amount of CPU or memory the Kubernetes scheduler reserves for a container. The sum of all requests on a node cannot exceed what that node offers, so requests decide how many pods fit.
  • A limit is the ceiling a container may consume. Exceeding a memory limit gets the container killed and restarted.
Note

A node advertised as 8 GiB does not offer a full 8 GiB to your workloads. EKS reserves memory and CPU for the kubelet, the container runtime and system DaemonSets. Budget roughly 85-90% of the advertised figure as usable.

Node Group Sizing

Node groups

The cluster layer creates two managed node groups:

Node group Purpose Default instance type Default count
system Cluster controllers - Envoy Gateway, cert-manager, External Secrets Operator, AWS Load Balancer Controller, Istio t3.medium (2 vCPU, 4 GiB) 1
app XMPro product pods, one set per site t3.large (2 vCPU, 8 GiB) 1 (min 1, max 3)

The app default of a single t3.large is below what a site needs to install successfully, and the count cannot be changed once the node group exists. Read Translating requests into node size and count and Scaling out before your first apply of the cluster layer.

Per-product resource requests and limits

These are the chart defaults, applied to every site. Note there are no CPU limits - .NET startup is CPU-hungry and throttling it makes pods slow to become ready. Memory limits are set because memory is not compressible.

The last two columns are what the scheduler actually reserves. enable_istio defaults to true, so every site namespace is labelled istio-injection=enabled and every product pod gets an Istio sidecar that requests a further 25m CPU and 128 Mi. Size against those columns, not the chart request.

Product CPU request Memory request Memory limit Effective CPU (with sidecar) Effective memory (with sidecar)
AD (App Designer) 150m 1 Gi 4 Gi 175m 1152 Mi
DS (Data Stream Designer) 150m 2 Gi 4 Gi 175m 2176 Mi
SM (Subscription Manager) 100m 512 Mi 1 Gi 125m 640 Mi
IS (Identity Server) 100m 1 Gi 2 Gi 125m 1152 Mi
AI 25m 384 Mi 768 Mi 50m 512 Mi
Stream Host 25m 256 Mi 512 Mi 50m 384 Mi
Note

The sidecar is not free, and it is not optional by default. Istio 1.30 runs istio-proxy as a native sidecar - an initContainer with restartPolicy: Always - so Kubernetes computes the pod's effective request as max(sum of regular initContainers, sum of sidecars + sum of containers). The sidecar's 25m CPU and 128 Mi are therefore added to the product's own request, not absorbed by it. The cluster layer sets the proxy CPU request to 25m and leaves memory at the Istio default of 128 Mi. Deploying from environments/site-template/app with enable_istio = false removes this overhead; the examples/layered/app example always injects.

Translating requests into node size and count

A site running SM, IS, AD and DS requests 500m CPU and 4.5 GiB from the product containers alone. With the default Istio injection, the four sidecars add 100m CPU and 512 Mi, so the real steady-state figure is 600m CPU and 5120 Mi (5 GiB). Adding the AI product takes it to 650m and 5632 Mi (5.5 GiB).

Steady state is not what sizes the node - the install peak is. During an install the three database-migration Jobs and the licensing Job run concurrently with the products, and each of those Jobs is sidecar-injected too. On a measured single-site install the application node peaked at 5324 Mi of 7078 Mi allocatable (75%) with 12 pods resident before the Jobs completed and released their memory.

Warning

A single t3.large application node cannot complete an install. With the shipped default of app_node_count = 1, the install failed: xmpro-ds never scheduled (FailedScheduling: 0/2 nodes are available: 2 Insufficient memory), the Helm release ran out its 1800-second timeout, and because the release is applied atomically the entire install was rolled back - leaving nothing to inspect and no partial site to repair.

Budget for the peak, not the steady state. The realistic floor for one site is two t3.large application nodes, or a single application node of at least 16 GiB (t3.xlarge, or m6i.xlarge for production). Add a node per additional site on the same cluster.

Memory is the binding constraint, not CPU. If you are deciding what to grow, grow memory.

Node group knobs

Set these in the cluster layer's terraform.tfvars:

Variable Default Controls
system_node_instance_type t3.medium Instance type for cluster controllers
system_node_count 1 Number of system nodes
app_node_instance_type t3.large Instance type for product pods
app_node_count 1 Desired application nodes, applied at node group creation only - see Scaling out
app_node_min_count 1 Lower bound for the node group
app_node_max_count 3 Upper bound for the node group
node_az_count 1 How many AZs the node groups span
gateway_eip_az_count 0 Public AZs the gateway NLB spans (0 = match node_az_count)
single_nat_gateway true One shared NAT gateway instead of one per AZ

Scaling out

Because a single replica per product is the supported topology today (see the autoscale note in the deployment guide), you scale a cluster by adding nodes for additional sites, not by adding replicas of one site. Budget the floor from Translating requests into node size and count for each site you add.

Important

app_node_count binds when the node group is created and never again. The upstream EKS node group module deliberately ignores changes to the group's desired size after creation, because cluster autoscalers are expected to own that value at runtime. Raising app_node_count on an existing cluster plans clean and does nothing: terraform apply reports Apply complete! Resources: 0 added, 0 changed, 0 destroyed. and the node count is unchanged. Size the application node group before the first apply of the cluster layer.

To resize a node group that already exists, change its scaling configuration directly:

aws eks list-nodegroups --cluster-name <cluster>

aws eks update-nodegroup-config --cluster-name <cluster> --nodegroup-name <ng> \
  --scaling-config minSize=1,maxSize=3,desiredSize=2

app_node_min_count and app_node_max_count still update the group's bounds through Terraform, but bounds alone create no nodes - the desired size is what does, and after creation only the command above (or an autoscaler) moves it. Set maxSize in the same command when the new desired size would exceed the current upper bound.

Production notes

  • t3 instances are burstable. They accrue CPU credits when idle and throttle when exhausted. That is fine for evaluation and poor for sustained production load. Move to m6i or m7i for production.
  • node_az_count = 1 is single-AZ. The default keeps cost down by confining nodes to one availability zone, which means an AZ failure takes the site down. Raise it for real availability, and raise gateway_eip_az_count with it so the gateway NLB spans the same AZs.
  • AZ width alone does not spread the workload. node_az_count only widens where nodes may be placed. With the defaults of system_node_count = 1 and app_node_count = 1 there is still exactly one node of each type, and single-replica products still all land in one AZ. Raise system_node_count to at least 2 and app_node_count to at least one node per AZ you want covered, so the node groups actually have nodes in more than one zone. Do this before the first apply of the cluster layer - afterwards the app group has to be resized with aws eks update-nodegroup-config (see Scaling out).
  • single_nat_gateway = true is a single point of failure and a cost saving. Set it false for production.

Database Sizing

The site infrastructure layer creates one RDS SQL Server instance per site.

Variable Default Notes
db_engine sqlserver-ex SQL Server Express
db_engine_version 15.00 SQL Server 2019
db_instance_class db.t3.small 2 vCPU, 2 GiB
db_allocated_storage 20 GiB
rds_backup_retention_period 1 Days
rds_deletion_protection false Dev default - enable for production
rds_skip_final_snapshot true Dev default - disable for production
Warning

SQL Server Express has a hard 10 GB per-database cap and is limited to roughly 1.4 GB of RAM and 4 cores regardless of the instance class you pick. It is suitable for evaluation only. Use sqlserver-se (Standard) or higher for production, and size db_instance_class to at least db.t3.medium.

Production database checklist

  • [ ] db_engine set to sqlserver-se or higher
  • [ ] db_instance_class sized for your workload, not left at db.t3.small
  • [ ] db_allocated_storage raised above 20 GiB
  • [ ] rds_backup_retention_period raised to your retention policy
  • [ ] rds_deletion_protection = true
  • [ ] rds_skip_final_snapshot = false

Cost

The main billable components of a single-site development deployment are:

Component Default size Quantity
EKS control plane - 1 per cluster
System node t3.medium 1
Application node t3.large 2 per site (the install floor)
RDS instance db.t3.small, sqlserver-ex, 20 GiB 1 per site
NAT gateway - 1 (shared, single_nat_gateway = true)
Network Load Balancer - 1 (shared across all sites on the cluster)
Elastic IP - 1 per gateway AZ
Route53 hosted zone - 1 per site
EBS volumes gp3, node root disks 1 per node

Prices vary by region and change over time, so this guide does not quote figures. Price the components above for your own region using AWS's published pricing:

  • AWS Pricing Calculator - build a full estimate from the table above
  • Amazon EKS pricing
  • Amazon EC2 pricing - node instance types
  • Amazon RDS for SQL Server pricing
  • Amazon VPC pricing - NAT gateways
  • Elastic Load Balancing pricing
  • Amazon Route53 pricing

The two largest cost levers, in order, are NAT gateways (single_nat_gateway = false multiplies both the hourly charge and per-AZ data processing) and node instance type and count.

Sharing one cluster across many sites is what makes this architecture economical - the cluster, its controllers, the NAT gateway and the load balancer are paid for once and amortised across every site on it.
